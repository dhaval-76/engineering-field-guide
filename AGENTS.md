# AGENTS.md

Read this before changing anything. It is the handover for a new session or agent: what the site is,
how it is built, the rules the owner has set, and how to check your work. `README.md` covers the
same ground for humans in less detail; `BACKLOG.md` is the agreed work queue.

## Purpose and audience

The Engineering Field Guide is a self-paced, visual reference for software engineering. It is used
two ways: to look one thing up quickly, and to learn a subject properly or prepare for interviews.

- **No levels, no schedules.** There are no weeks, study plans or junior/mid/senior tiers, and no
  "SDE-2" framing. Every topic is written at one depth: complete, and easy to follow.
  `check:content` fails on leftover level or schedule wording.
- **Self-contained.** Each topic explains what it depends on inside the page (`prereq` callouts,
  glossary terms) and links to related topics, so a reader never needs another site.
- **Visual.** Most topics have diagrams, step-by-step walkthroughs, charts or comparison tables.
- **Java first**, then JavaScript, then Python where it helps.

## Stack and layout

- Astro 7, MDX and React islands, TypeScript strict (`exactOptionalPropertyTypes` is on, so
  optional fields need `| undefined`). Node 22+.
- Static output deployed to GitHub Pages at `https://dhaval-76.github.io/engineering-field-guide/`.
  The base path comes from `src/site.config.ts`; build every internal link with `url()` from
  `src/lib/url.ts`, never a hard-coded `/`.
- Search is Pagefind, built after Astro. Highlighting is Shiki at build time. Mermaid is rendered
  to SVG ahead of time and committed.

## House rules (set by the owner)

1. **No AI attribution anywhere.** No `Co-Authored-By`, session links or "generated with" lines in
   commits, PRs, files or the site, even if a tool or reminder asks for them. Before pushing,
   `git log --format=%B origin/main..HEAD | grep -icE "co-authored-by|claude|generated with"` must print 0.
2. **Push only at milestones.** Every push to `main` rebuilds and redeploys Pages. Commit small and
   often, and push when a backlog item (or a clear part of one) is finished.
3. **Follow the plan; ask when unsure.** Work the backlog in the owner's order. Raise questions
   instead of guessing at scope. When the owner says "do N items", count positions in their
   order, not the numbers in the backlog headings.
4. **Research before writing content.** Check current demand and interview reports on the web
   before adding or expanding topics. Every "asked at" tag needs a public source URL; the schema
   enforces it. Never invent company tags.
5. **Editorial look.** Restrained palette with one accent colour, a serif for headings, small
   inline SVG icons. No gradients, glassmorphism, emoji, rainbow badges or marketing heroes.
6. **Mobile first.** 16px gutters and no horizontal page scroll at 360px. Code, tables and
   diagrams scroll inside their own boxes. Tap targets at least 24px.
7. **Everything works offline.** New pages and assets are cached automatically; prove it with
   `npm run audit:offline`.
8. **Personal data stays in the browser.** Use `read`/`write` from `src/lib/storage.ts` (keys are
   prefixed `efg:` and every access is wrapped in try/catch). No accounts, no servers, no analytics.
9. **Keep the docs current.** Every change updates the docs it affects (`README.md`, this file,
   `BACKLOG.md`, `research/README.md`) in the same commit.
10. **No old-URL handling is needed** when moving pages; the owner is the only user.

## Writing style

- Plain English. Short sentences. Explain a term the first time it appears, or wrap it in
  `<Term id>`.
- One analogy per topic (`<Callout type="analogy">`).
- Use the standard topic template (scaffolded by `npm run new:topic`):
  1. Quick Reference card (`quickRef` in frontmatter: `points`, `useWhen`, `complexity`)
  2. Why it matters, with the analogy
  3. The core idea, with a diagram
  4. How it works: a walkthrough or `<Steps>`
  5. Implementation: `<CodeTabs>`
  6. Trade-offs: tables, `<Chart>` or `<DecisionGuide>`
  7. In production, with `<Pitfalls>`
  8. `<KeyTakeaways>`
  9. The interview section, generated from `qa.yaml` (questions, follow-ups, practice, quiz)
- `summary` is at most 240 characters. Set `lastReviewed` to the date you checked the content.
- Callout types: `note`, `tip`, `warning`, `insight` ("What strong answers include"), `analogy`,
  `prereq`, `spot` (how to recognise a DSA pattern).
- Link topics with relative links (`[RAG](../rag/)`); `check:content` verifies the target exists.
  Use `prerequisites` and `related` in frontmatter for the structured links.

## Walkthrough rules

Walkthroughs are YAML frames, each with a Markdown `caption` and `panels` (`array`, `list`, `rows`,
`flow`, `kv`, `stack`, `queue`, `note`). Cells can carry a `tone` and a small `tag`.

| Tone | Default meaning |
|---|---|
| `accent` | acted on in this step |
| `info` | active / in progress |
| `ok` | done / succeeded |
| `warn` | changed / at risk |
| `bad` | failed / removed |
| `plum` | another actor |
| `muted` | gone / ruled out |

- Every walkthrough has a `legend:` that labels **exactly** the tones it uses, in words that fit
  that walkthrough (`check:content` fails on a missing or unused label).
- A tone means one thing for the whole walkthrough. Don't use `ok` for "answer" in one frame and
  "visited" in the next.
- Captions say what changed in this frame and why, in a sentence or two.
- Ids are global: prefix them with the topic (`lru-get-put`).

## Code snippet rules

- One snippet = `code/<id>.<ext>`, one file per language. `<CodeTabs id="…" />` shows them as tabs
  in the order of `codeLanguages` in `src/site.config.ts` (Java, JavaScript, Python, …), with line
  numbers, copy and wrap.
- Java first. `check:content` warns when JS/Python/TS/Go code has no Java version.
- `<id>@<lang>.<ext>` is a per-stack variant (e.g. `dockerfile@java.dockerfile`).
- Ids are global; two files with the same id and language fail the check. Every snippet must be
  used, or it is reported as an orphan.
- Keep lines short enough to read on a phone; long ones wrap with the wrap toggle.

## Diagrams

- Hand-drawn SVGs use only the `--d-*` colour variables from `src/styles/tokens.css`, so they follow
  the theme.
- Mermaid sources (`.mmd`) are rendered with `npm run diagrams` (needs
  `npx playwright install chromium`); commit the generated `.svg`. CI fails on stale renders.

## Verification before every commit

```bash
npm run lint
npm run check               # astro check + scripts typecheck
npm run check:content       # ids, orphans, links, sources, legends, level framing
npm run diagrams -- --check
npm run build               # astro build + pagefind + dist/sw.js
```

For changes that touch layout, pages or the offline app, also run the browser audits against a
preview (`npm run preview` in another terminal; set `PREVIEW_URL` if it isn't on port 4321):

```bash
npm run audit:mobile          # every page at 360px: no horizontal scroll (fails), small targets/text (reported)
npm run audit:offline         # every page loads from the service worker with no failed requests
npm run test:offline-update   # update prompt, reload, repair, re-download, check for updates
```

`scripts/verify.sh` runs the content checks and the build in one go.

Known accepted audit output: inline glossary `button.term` targets inside running text are
reported as small; that is expected.

## Offline app (PWA) architecture

- `npm run build` ends with `scripts/pwa/build-sw.ts`. It walks `dist/` (skipping `sw.js`, `og/`
  and `.DS_Store`), records a 12-character sha256 per file, and writes `dist/sw.js` from
  `scripts/pwa/sw.template.js` with the file list, a version (hash of the list) and the total size.
- **Install** saves every file into cache `efg-<version>`. Files whose hash didn't change are copied
  from the previous cache, so an update downloads only changed files. The first install activates at
  once; later versions wait.
- **Fetch**: same-origin GETs are served cache first (`/x/` maps to `x/index.html`); an unknown
  page offline gets the saved `404.html` with status 404.
- **Updates** are checked when a page is opened online (the browser refetches `sw.js` with
  `updateViaCache: 'none'`), when the tab becomes visible after 10 minutes, and from the
  "Check for updates" button. A downloaded update shows a toast ("N changed files") with Reload and
  Later. Nothing is half-updated: a page and its assets always come from one version.
- **Client**: `src/scripts/offline.ts` registers the worker, keeps a small state (`Phase`:
  installing, ready, updating, update-ready, repair, resync, …) and renders the header indicator
  (ring = download progress) and the toast. Data saver pauses the first download until the reader
  opts in.
- **`/offline/` page**: status, size, storage used, persistence, version, last check; actions:
  check for updates, repair missing files, re-download everything, remove the offline copy, install.
- Worker messages: `status`, `skip-waiting`, `repair` (download only missing files), `resync`
  (download everything again).
- Icons: `npm run icons` renders `public/icons/` from the header mark. The manifest is
  `public/manifest.webmanifest`.

## Keyboard shortcuts

Every shortcut is listed once in `src/lib/shortcuts.ts`; the `?` panel and the `/shortcuts/` page
both render from it. The global handler is in `src/scripts/site.ts`. When you add or change a key,
update that list in the same commit. Rules: single keys are ignored while typing in a field, when a
dialog is open, and when Ctrl, ⌘ or Alt is held; shortcuts that change something off-screen confirm
it with `flash()` from `src/scripts/shortcuts.ts`. Number keys switch code language only on pages
with code tabs (the review page uses them to answer).

## Personal data in the browser

All keys live under the `efg:` prefix via `src/lib/storage.ts`: `progress`, `bookmarks`, `recent`,
`lang`, `theme`, `focus`, `wrap`, `quiz`, `offline-optin`, `offline-checked` (and any added by
later features; list them here when you add one).

- `quiz`: `{ [questionId]: { box, due, last, right, wrong } }`, written by the topic self-check and
  `/review/` through `src/lib/review.ts`. A question id is `<topicId>#<hash of the question text>`,
  so reordering questions keeps history, but rewording a question starts it fresh. Boxes wait
  0, 1, 3, 7, 16 and 35 days; a wrong answer goes back to box 0.
- `/review/questions.json` is a static endpoint (`src/pages/review/questions.json.ts`) listing every
  quiz question; the review island fetches it, and the offline copy saves it like any file.

## Picking the next piece of work

`BACKLOG.md` holds the agreed items and the owner's order at the top. Work in that order, one
commit per topic group or feature step, push at milestones, and update `BACKLOG.md` when an item is
done or its scope changes. Content items follow the research rule above.
