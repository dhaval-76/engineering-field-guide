## Why it matters

Java changed more between 8 and 21 than in the decade before. Interviews for Java roles now expect you to know at least records, sealed types, pattern matching and <Term id="virtual-thread">virtual threads</Term> — and why they exist. They also make everyday code shorter and safer: algebraic data types with exhaustive `switch`, data classes in one line, and simple blocking code that scales.

<Callout type="analogy">
Upgrading from a manual toolbox to power tools. The old tools still work, and you can build the same things — but jobs that took a page of careful work now take a line, and the new tools have safety guards built in.
</Callout>

## Modelling data: records, sealed types, pattern matching

<CodeTabs id="modern-sealed-patterns" title="A closed result hierarchy, deconstructed with an exhaustive switch" />

Together these give Java **algebraic data types**:

- **Records** are concise <Term id="immutable">immutable</Term> data carriers.
- **Sealed** interfaces list every permitted implementation, so the compiler knows the full set.
- **Pattern matching `switch`** with **record patterns** deconstructs values and must be **exhaustive** over a sealed type — add a new case and every switch that doesn't handle it stops compiling.

This is often a cleaner alternative to the Visitor pattern, or to a class hierarchy where behaviour belongs outside the types (rendering, serialisation, reporting). Keep polymorphic methods when the behaviour belongs *with* each type (Strategy/State).

## Concurrency: virtual threads

<CodeTabs id="modern-virtual-threads" title="Thousands of blocking calls on virtual threads" />

A **virtual thread** is a thread managed by the JVM rather than the OS. When it blocks on I/O, the JVM unmounts it from its carrier (platform) thread, which runs other virtual threads meanwhile. You keep simple, sequential blocking code — no callback chains — and handle tens of thousands of concurrent requests.

- **Good for**: I/O-bound work — HTTP calls, database queries, message handling.
- **Not for**: CPU-bound work (it still needs cores) — keep bounded platform pools there.
- **Don't pool** virtual threads; create one per task. Limit concurrency to fragile downstreams with a <Term id="semaphore">semaphore</Term>, not a small pool.
- Since Java 24, `synchronized` no longer pins a virtual thread to its carrier; on 21–23 prefer `ReentrantLock` around blocking calls.

## Newer stream and context APIs

<CodeTabs id="modern-gatherers" title="Gatherers for batching and windows; scoped values for request context" />

- **Stream gatherers** (24) let you write custom intermediate operations; built-ins include fixed and sliding windows, folds and scans.
- **Scoped values** (25) pass immutable per-request data (user, trace id) down a call tree — and to child tasks — without `ThreadLocal`'s mutability and leak risks.
- **Structured concurrency** (preview in 25) treats a group of concurrent subtasks as one unit with shared cancellation and error handling.

## Upgrading from Java 8

- Move to 17 or 21 first (both LTS); 25 is the newest LTS.
- Expect work around the module system (strong encapsulation of JDK internals), removed APIs (Java EE modules like JAXB were removed in 11), and library upgrades (Spring Boot 3 and 4 both require 17+).
- Adopt features gradually: records for DTOs, switch expressions, text blocks, then sealed types and virtual threads where they fit.

<Pitfalls>

- **`var` everywhere** — hides types where the right-hand side doesn't make them obvious.
- **Records for JPA entities** — entities need mutability and no-arg constructors; use records for DTOs and value objects.
- **Pooling virtual threads or running CPU-bound work on them.**
- **`default` branches on sealed switches** — they defeat the exhaustiveness check you wanted.
- **Preview features in production** — they can change between releases and need `--enable-preview`.

</Pitfalls>

<KeyTakeaways>

- Records + sealed types + pattern matching = concise, exhaustive data modelling.
- Switch expressions, text blocks, `toList()`, sequenced collections and `_` simplify daily code.
- Virtual threads scale blocking I/O; keep CPU work on bounded pools.
- Target an LTS (17/21/25) and adopt features incrementally.

</KeyTakeaways>
