## Why it matters

In Google Docs-style editors several people type into the same document at once, each seeing their own edits instantly, and everyone must end up with exactly the same text even though their edits crossed on the network. Sending whole documents back and forth can't work; the design sends small operations and needs a way — Operational Transformation or CRDTs — to merge concurrent edits deterministically, plus cursors, presence and offline editing.

<Callout type="analogy">
Several editors marking up copies of the same manuscript by phone. Each says "insert 'quickly' after word 12"; if one of them just deleted word 5, everyone else must shift that instruction to word 11 before applying it — then all the copies stay identical.
</Callout>

## Requirements

**Functional**: several people edit the same document simultaneously and see each other's changes within ~100–200 ms; see collaborators' cursors and selections; edit offline and sync later; version history; comments; permissions (view, comment, edit).
**Non-functional**: no lost edits; every participant converges to the same document; tens of millions of documents, most idle; popular documents with hundreds of concurrent editors and thousands of viewers.

## The core problem

Two people edit the same text at the same time. Locking (one editor at a time) destroys the experience; last-write-wins loses work. Both edits must apply, and all copies must end up identical.

## OT or CRDT

| Aspect | Operational transformation | CRDTs (e.g. Yjs, Automerge) |
|---|---|---|
| Idea | server orders ops; concurrent ops are rewritten against each other | each element has a unique position id; ops commute by construction |
| Needs a central server? | yes — it defines the order | no — any order of delivery converges |
| Offline / peer-to-peer | harder (long-diverged histories) | natural |
| Metadata | small | per-element ids and tombstones (compacted over time) |
| Used by | Google Docs and many classic editors | many newer editors, local-first apps; Figma uses CRDT-inspired, server-authoritative structures |

Either way, the architecture around the algorithm is similar.

## Architecture

<Diagram id="collab-architecture" caption="All editors of a document connect to the session server that owns it; it sequences ops, appends them to a log and broadcasts them." />

- **Routing**: a document id maps to one **session server** (consistent hashing or a lease in a coordination store); every client editing that document connects there (or through a gateway that forwards). Having one owner makes ordering simple.
- **Ops flow**: client applies its op locally → sends `{docId, baseRevision, op, clientOpId}` → the session server transforms it against ops since `baseRevision`, assigns the next revision, appends it to the **op log** (durable before acking), broadcasts it → clients transform any of their pending ops and apply.
- **Snapshots**: every N ops (or minutes) the server stores a full snapshot; loading a document = latest snapshot + ops after it. Old ops can be compacted after the version-history policy allows.
- **Failover**: if the session server dies, the lease moves; the new owner loads snapshot + log and clients reconnect, resending unacknowledged ops (de-duplicated by `clientOpId`).

## Presence, cursors and comments

Cursor positions and selections are **awareness** messages: throttled (e.g. 10/s), sent only to the document's session, never persisted; they must be transformed (or anchored to element ids) so they stay in the right place as text changes. Comments anchor to ranges by stable ids (CRDT ids or OT-transformed positions).

## Offline and permissions

Offline clients queue ops locally; on reconnect they send them with their last known revision. With OT the server transforms the whole batch; with CRDTs merging is automatic. Permissions are checked when joining a session and on every op (viewers' ops are rejected); revoking access disconnects the user's sessions.

## Scale

Most documents are idle: session servers hold only active documents in memory and unload them after inactivity. A document with thousands of viewers fans out broadcasts through a pub/sub tier; editors stay on the owner. Op logs go to a write-optimised store; snapshots to object storage or a database.

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| The document's session server crashes | a brief reconnect | clients reconnect to a new server, which loads the latest snapshot plus the operation log |
| A user goes offline | they keep typing | edits are stored locally and merged on reconnect (OT rebase or CRDT merge) |
| An operation is delivered twice | nothing | operations carry client id + sequence number and are applied once |
| The operation log storage is slow | edits lag | the session server batches writes; acknowledgements wait for durability so nothing is lost |

<Pitfalls>

- **Sending whole documents** on every keystroke.
- **Last-write-wins** — silently discards collaborators' edits.
- **Several servers accepting ops for one document** without a single sequencer (OT) or a CRDT.
- **Acknowledging before the op is durable.**
- **Persisting cursors**, or broadcasting them unthrottled.
- **Unbounded op logs** with no snapshots.

</Pitfalls>

<KeyTakeaways>

- Ops, applied optimistically and sequenced by one owner per document (OT), or merged by CRDTs.
- Op log + snapshots for durability, history and fast loads.
- Ephemeral, throttled presence; ops de-duplicated by client id on reconnect.
- Route by document id; unload idle documents; fan out to viewers via pub/sub.

</KeyTakeaways>
