## Why it matters

Live dashboards — active users now, sales per minute, the top trending items — must turn millions of events per second into numbers with seconds of delay. Events arrive late and out of order, exact counts over huge cardinalities are expensive, and the numbers must be correct after a crash or a replay. The design covers stream processing with windows and watermarks, approximate algorithms (HyperLogLog, Count-Min sketch) and OLAP stores built for fast aggregation.

<Callout type="analogy">
Counting votes at a large election in real time. Tally clerks count ballots by district every few minutes and post running totals, late ballots from remote areas are added to the right period when they arrive, and the final official count is reconciled from the stored ballots later.
</Callout>

## Requirements

**Functional**: live dashboard (events per second, revenue per minute, unique users in the last hour, top 10 products right now); historical queries (revenue by product by day for 90 days, filter by country/device); alerts on anomalies.
**Non-functional**: 1–5 M events/s at peak; dashboard lag < a few seconds; historical queries < 2 s; counts correct even with retries and late mobile events; reprocess when logic changes.

## Estimates

5 M events/s × ~200 bytes ≈ 1 GB/s ≈ 86 TB/day raw — raw events go to compressed columnar files in object storage (Parquet, ~10× smaller); dashboards read rollups that are orders of magnitude smaller (per minute × dimensions).

## Windows and late data

<Walkthrough id="windows-watermarks" />

| Window | Shape | Example |
|---|---|---|
| Tumbling | fixed, non-overlapping | orders per minute |
| Sliding / hopping | fixed size, overlapping | rolling 5-minute average every 10 s |
| Session | per key, closes after inactivity | user sessions with a 30-minute gap |

- **Event time** (when it happened) vs **processing time** (when it arrived): use event time for correct numbers; mobile clients may send events minutes or hours late.
- A **watermark** says "we've probably seen everything up to time T". Windows emit when the watermark passes their end; **allowed lateness** updates results for stragglers; anything later goes to a side output (and is fixed in batch).
- **<Term id="exactly-once">Exactly-once</Term> results**: the processor checkpoints its state together with Kafka <Term id="offset">offsets</Term> (Flink checkpoints, Kafka Streams transactions), and sinks are <Term id="idempotency">idempotent</Term> (upsert by window + key).

## Counting at scale

<CodeTabs id="sketches" title="Unique users with HyperLogLog, top-K with Count-Min Sketch and a heap" />

| Question | Exact approach | At scale |
|---|---|---|
| How many events? | counter per window | sharded counters, pre-aggregation in the stream |
| How many **unique** users? | set of ids (memory grows with users) | HyperLogLog: ~12 KB per counter, ~0.81% standard error (Redis), mergeable across windows |
| Which items are **top-K**? | count every item, sort | Count-Min Sketch + min-heap, or count per partition and merge top-K candidates |
| Percentiles (p99 latency)? | sort all values | t-digest / HDR histograms |

## Storage and serving

- **Live**: the processor writes current window results to <Term id="redis">Redis</Term> or the OLAP store's real-time ingestion; dashboards read the latest few minutes.
- **Historical**: rollups (e.g. per minute → hour → day, by product, country, device) in a columnar OLAP store, partitioned by time and sorted by common filters; a 90-day revenue query reads a few thousand rows, not billions.
- **Raw events** in Parquet on object storage for ad-hoc analysis and reprocessing.
- **Reprocessing**: with logs retained (or the lake), fix a bug by replaying into new tables and switching — the **Kappa** approach. Lambda keeps a separate batch path that recomputes truth nightly, at the cost of two codebases.

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| A stream processing job crashes | dashboard freezes briefly | the job restarts from its last checkpoint and replays from the log; output is idempotent or transactional |
| Events arrive late | numbers revise slightly | watermarks allow lateness; late events update the right window, and very late ones go to a correction path |
| The OLAP store is down | dashboards unavailable | ingestion keeps writing to the log; the store backfills when it recovers |
| A traffic spike | dashboards lag | the log buffers the spike; consumers catch up; approximate counts keep memory bounded |

<Pitfalls>

- **Querying raw events for dashboards.**
- **Processing-time windows** for business metrics — late or replayed events land in the wrong minute.
- **Non-idempotent sinks** — reprocessing or failover double-counts.
- **Exact distinct counts in memory** for billions of ids.
- **<Term id="hot-partition">Hot keys</Term>** (one viral product) overloading one partition — pre-aggregate locally before the shuffle, or split the key.
- **No schema for events** — fields drift and pipelines break silently; use a schema registry.

</Pitfalls>

<KeyTakeaways>

- Kafka in, stream processing with event-time windows and watermarks, idempotent sinks.
- Sketches for uniques, heavy hitters and percentiles when exactness is too costly.
- Rollups in an OLAP store for queries; raw data in a lake; replay to fix and backfill.

</KeyTakeaways>
