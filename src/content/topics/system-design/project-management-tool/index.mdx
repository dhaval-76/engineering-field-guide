## Why it matters

Issue trackers like Jira or Linear look like simple CRUD, but each team wants its own workflow, fields and permissions, boards must update live when a colleague moves a card, and queries like "my open bugs in this sprint, ordered by priority" must be fast across millions of issues. The design is a good test of flexible schemas, permission checks on every read, search indexing and real-time updates in a multi-tenant product.

<Callout type="analogy">
A shared whiteboard of sticky notes in an open office. Each team draws its own columns, some notes are visible only to certain people, a note moved by one person moves for everyone watching, and a filing clerk keeps an index so anyone can ask "show me all notes about invoicing" without walking the whole office.
</Callout>

## Requirements

**Functional**: projects with issues (type, title, description, status, assignee, priority, labels, custom fields); configurable workflows per project; boards (kanban columns by status) and sprints; drag-and-drop ordering; comments with @mentions; watchers and notifications; search with structured filters ("assignee = me AND status != Done"); per-project permissions; audit history.
**Non-functional**: 10,000+ organisations, 10 M users, billions of issues; board load < 1 s even with thousands of issues; changes visible to other viewers within seconds; strong tenant isolation.

## Estimates

Reads dominate (boards, issue views, search) — perhaps 50:1. Writes ≈ a few thousand issue changes per second globally; each change fans out to watchers, search and live boards. Issue rows are small (~2 KB) but descriptions and attachments are not — attachments go to object storage.

## Data model and workflows

<CodeTabs id="tracker-model" title="Issues, data-driven workflows and transitions" />

- A **workflow** is per project (or shared scheme): states, allowed transitions, and transition rules (required fields, who may transition, post-actions such as "assign to reviewer").
- Transitions use **<Term id="optimistic-locking">optimistic concurrency</Term>** (issue version) so two people dragging the same card don't silently overwrite each other.
- Custom fields: typed definitions per project, values in a JSONB column or an entity-attribute table; indexed into search for filtering.
- Every change appends to an **issue history** (field, old, new, actor, time) — the activity log, audit trail and source for notifications.

## Boards

<Walkthrough id="board-reorder" />

- Board load: column counts (one grouped, indexed query or cached counts) + the first page of cards per column, cursor-paginated; more cards load on scroll.
- **Ordering**: a rank string per card; moving a card computes a key between its new neighbours — one row updated, not thousands renumbered. Occasional rebalancing keeps keys short.
- **Live updates**: board viewers subscribe to the project's channel over WebSocket/SSE; change events are pushed to them; on reconnect they refetch.

## Search and filters

Users' structured queries (a JQL-like language) are parsed into a search-engine query with the user's permission filter added; issues are indexed from change events ([Search](../search-engine/)). Saved filters drive dashboards and boards; heavy aggregations ("issues created per week") use the analytics path rather than the transactional database.

## Notifications and mentions

Comment saves parse `@mentions` and emit events; a notification service resolves recipients (watchers, assignee, mentioned users), applies preferences, de-duplicates and batches (one digest instead of ten emails), and delivers in-app, email or chat-integration messages.

## Permissions and tenancy

Permission schemes map project roles to actions (browse, create, transition, administer); issue-level security can restrict sensitive issues to groups. Effective permissions are cached per (user, project) and invalidated on role changes; search queries include them as filters. Data is keyed by tenant, with enterprise tenants placed on dedicated shards ([Multi-tenant data](../../databases/multi-tenant-schema/), [Auth at scale](../auth-at-scale/)).

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance. For services that publish events, the general patterns — circuit breakers, spooling, ordered replay — are in [Surviving dependency outages](../../distributed-systems/failure-fallbacks/).

| What fails | What users see | What the design does |
|---|---|---|
| The search index lags or is down | new issues missing from search | boards and issue pages read the primary database; search catches up from the change stream |
| Live updates are disconnected | board doesn't refresh itself | clients reconnect and refetch the board; edits still work through the API |
| One tenant runs a huge import | others unaffected | per-tenant rate limits and separate queues for bulk work |
| The notification service is down | late emails or mentions | notifications are queued from the outbox and sent when it recovers |

<Pitfalls>

- **Hard-coded statuses** — every customer wants their own workflow.
- **Integer positions for card order** — moving one card renumbers the column.
- **Loading every issue of a sprint** for the board.
- **`LIKE` queries for search** and filters in the transactional database.
- **Notifying on every field edit** — batch and respect preferences.
- **Last-write-wins on concurrent edits** without version checks.

</Pitfalls>

<KeyTakeaways>

- Clarify scope; model workflows, fields and permissions as data.
- Change events feed history, notifications, search and live boards.
- Boards: counts + paginated columns + rank keys.
- Search index with permission filters; tenant-keyed data and <Term id="sharding">sharding</Term>.

</KeyTakeaways>
