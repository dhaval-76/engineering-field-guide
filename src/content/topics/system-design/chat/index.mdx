## Why it matters

Chat looks simple — send a message, show it — but at hundreds of millions of users it combines the hardest pieces of real-time systems: millions of long-lived connections, delivering each message to the right server holding the recipient's connection, keeping messages **in order** per conversation, never losing one, syncing devices that were offline, and showing receipts and presence without flooding the network. Interviewers use it to test connection management, <Term id="fan-out">fan-out</Term> and ordering together.

<Callout type="analogy">
A postal service where every resident has a personal courier waiting at their door. A sorting office (the router) must know which courier serves which door, number every letter in a conversation so it's read in order, keep a copy until it's delivered, and hold mail for people who are away until they come back.
</Callout>

## Requirements

**Functional**: 1:1 and group messages (groups up to a few thousand); text and media; delivery and read receipts; online/last-seen presence and typing indicators; history sync across a user's devices; push notifications when offline.
**Non-functional**: 500 M users, 100 M daily active; 50 B messages/day; delivery under ~500 ms when online; no message loss once acknowledged; ordered within a conversation; very high availability.

## Estimates

50 B messages/day ≈ 600,000/s average, ~1–2 M/s at peak. At ~200 bytes each (plus metadata) ≈ 10–15 TB/day of new messages — a write-optimised, partitioned store with TTL/archival. Concurrent connections ≈ tens of millions; at ~100,000–500,000 connections per gateway host, that's hundreds of gateway servers.

## Storage and ordering

<CodeTabs id="chat-schema" title="Messages partitioned by conversation, ordered by sequence; per-device sync state" />

- Partition messages by **conversation** (bucketed by time for very active ones), cluster by **sequence number** — reading the latest page or catching up is one partition scan.
- The sequence number is assigned per conversation at write time (a counter in a strongly consistent store, or by the single owner of the conversation's partition). Timestamps from clients aren't reliable for ordering.
- The client sends a **client message id**; the server de-duplicates retries on it, so a flaky network can't create duplicates.
- Each device stores the **last sequence it has seen** per conversation; on reconnect it asks for everything after that.

## Delivery and routing

<CodeTabs id="chat-delivery" title="Accept, persist, then route to gateways or push" />

- A **session registry** (Redis/consistent store) maps `user → [(device, gateway)]` with TTLs refreshed by heartbeats.
- Routing to another gateway: publish to that gateway's channel (<Term id="redis">Redis</Term> pub/sub, or a per-gateway queue), or call it directly via an internal RPC.
- **Receipts**: "sent" when the server persisted it; "delivered" when a recipient device acknowledges; "read" when displayed — each is a small event routed back to the sender (and stored as per-member read pointers for groups, not per message).

## Groups

- Small and medium groups: look up members, route to the online ones' gateways, push to the offline ones (batched, with per-user notification preferences).
- Very large channels (thousands+): store once, notify lightly ("channel has new messages"), and let clients pull — the same push/pull trade-off as [news feeds](../news-feed/).

## Presence and typing

Presence is high-churn and disposable: gateways update `presence:{user}` with a short <Term id="ttl">TTL</Term> on each <Term id="heartbeat">heartbeat</Term>; subscribers (only the user's contacts who are currently online, or the open conversation) get changes — never broadcast every status change to everyone. Typing indicators are sent over the live connection only and never stored.

## End-to-end encryption

With the Signal protocol (used by WhatsApp and Signal), each device publishes public keys; senders derive per-conversation keys (X3DH) and ratchet keys per message (Double Ratchet), so the server stores and forwards only ciphertext. Consequences: server-side search, moderation and multi-device sync need client-side work (each device is a separate recipient), and backups must be encrypted by the client.

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| A connection server crashes | clients reconnect within seconds | clients reconnect to another server and resume from their last acknowledged message id |
| The recipient is offline | message delivered later | messages are stored before delivery is attempted; push notification; sync on reconnect |
| The message store is slow | sending spins | send is acknowledged only after a durable write; the client retries with the same message id, which de-duplicates |
| The message bus between servers is down | delays for users on other servers | messages are already durable; delivery catches up from storage when the bus recovers |
| Presence service overloaded | stale 'online' dots | presence is best-effort: degrade to less frequent updates; it never blocks messaging |

<Pitfalls>

- **Delivering before persisting** — a crash loses messages that the sender saw as sent.
- **Ordering by client timestamps.**
- **No client message id** — retries create duplicates.
- **Broadcasting presence to everyone** — the dominant load in naive designs.
- **Per-message read receipts in large groups** — store per-member read positions instead.
- **Sticky reconnect assumptions** — any gateway must be able to accept a reconnect and resync.

</Pitfalls>

<KeyTakeaways>

- Stateful gateways + a session registry route messages to live connections.
- Persist with a per-conversation sequence, then fan out; clients sync from their last sequence.
- <Term id="idempotency">Idempotent</Term> sends, push for offline users, receipts as events.
- Presence ephemeral and scoped; big channels pull instead of push.

</KeyTakeaways>
