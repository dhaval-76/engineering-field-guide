## Why it matters

Automation platforms like Zapier or n8n let users chain steps — "when a form is submitted, create a CRM contact, then send a Slack message". The engine must run millions of user-defined workflows reliably: resume exactly where it stopped after a crash, retry failed steps without repeating finished ones, respect each third-party API's rate limits, and keep users' credentials safe. It's a good test of durable execution and idempotency.

<Callout type="analogy">
A recipe card that a relay of cooks follows. Each finished step is ticked on the card, so if a cook goes home mid-recipe, the next cook continues from the last tick instead of starting over — and never adds the salt twice.
</Callout>

## Requirements

**Functional**: users build workflows — a trigger ("new row in a spreadsheet", "webhook received", "every Monday 9:00") followed by actions ("call an AI model", "create a ticket", "send a Slack message"), with conditions, branches, loops over lists and data mapping between steps; view run history and retry failed runs; connect accounts via OAuth.
**Non-functional**: millions of workflows, tens of thousands of runs per second at peak; runs must not be lost or silently half-done; third-party APIs are slow, rate-limited and flaky; one tenant's surge mustn't starve others.

## Definitions as data

<CodeTabs id="workflow-definition" title="A workflow definition and the run/step tables" />

- Definitions are **versioned**: a run always executes the version it started with; editing a workflow creates a new version.
- Validate at save time: the graph is acyclic (or loops are bounded), referenced fields exist, connectors are authorised.
- Data mapping between steps uses a safe template/expression language (JSONata, CEL) — never `eval` of user input.

## Durable execution

<Walkthrough id="run-resume" />

<CodeTabs id="workflow-engine" title="Advancing a run one step at a time, safely" />

- The engine is **stateless**: workers take "execute step N of run R" tasks from a queue, load the run's state, execute, persist the step result and enqueue the next step(s) — in that order, with the next-step enqueue in the same transaction as the result (outbox).
- A crash anywhere means the step task is redelivered; because results are persisted and steps carry idempotency keys (`run-id:step-id`), re-execution is safe and completed steps are skipped.
- Waits ("delay 3 days", "wait for approval") are timers, not sleeping threads: the run parks with a wake-up time ([Job scheduler](../job-scheduler/)).
- General-purpose engines (Temporal, AWS Step Functions, Camunda) provide exactly this durable-execution model if you don't build your own.

## Triggers

| Trigger | How | Watch out |
|---|---|---|
| Webhook | the source calls our endpoint per event | verify signatures; de-duplicate event ids; respond fast and queue |
| Polling | fetch "changes since cursor" on a schedule | store the cursor per workflow; respect API limits; latency = poll interval |
| Schedule | cron rule per workflow | time zones; overlapping runs |
| App events | internal event bus | fan-out to many workflows listening to the same event |

## Calling third parties

- **Per-connector, per-account rate limiters** — a 429 means "wait `Retry-After`", parking the step rather than holding a worker.
- Retries with exponential backoff for timeouts and 5xx; no retries for 4xx validation errors; idempotency keys where the API supports them.
- **Credentials**: OAuth tokens encrypted at rest (envelope encryption with a KMS), refreshed proactively, scoped to the minimum needed.
- Separate worker pools (bulkheads) per slow connector so one failing API can't block all runs.

## Multi-tenancy and safety

Per-tenant concurrency limits and fair queues (a tenant with a million-row import shouldn't delay everyone), step and run limits (max steps, max runtime, max loop iterations), sandboxed execution for user code steps (isolated containers or WASM with CPU/memory/network limits), and audit logs of every run. Run payloads may contain personal data — retention limits and redaction in logs. See [Multi-tenant data design](../../databases/multi-tenant-schema/).

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance. For services that publish events, the general patterns — circuit breakers, spooling, ordered replay — are in [Surviving dependency outages](../../distributed-systems/failure-fallbacks/).

| What fails | What users see | What the design does |
|---|---|---|
| A worker crashes mid-workflow | the run continues | each step's result is persisted; the run resumes from the last completed step |
| A third-party API is down | steps wait and retry | retries with backoff; per-integration circuit breakers; the run pauses rather than failing at once |
| A step succeeded but its result wasn't saved | a step may repeat | steps are called with idempotency keys so a repeat is harmless |
| One tenant's workflow loops endlessly | nothing for others | per-run step limits, per-tenant quotas and timeouts |

<Pitfalls>

- **Keeping run state in worker memory** — a deploy loses every in-flight run.
- **Re-running a whole workflow on failure** — duplicate tickets, emails and charges from steps that already succeeded.
- **Sleeping threads for delays** instead of persisted timers.
- **Global rate limits** instead of per connector and account.
- **Plain-text OAuth tokens** or tokens in logs.
- **Unbounded loops or fan-out** from user definitions.

</Pitfalls>

<KeyTakeaways>

- Versioned definitions as data; a generic interpreter.
- Persist after every step; idempotent steps; resume rather than restart.
- Webhooks or cursor-based polling for triggers, de-duplicated.
- Per-connector rate limits, retries, bulkheads and encrypted credentials.
- Per-tenant fairness, limits and sandboxing.

</KeyTakeaways>
