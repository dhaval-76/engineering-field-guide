## Why it matters

Amazon's Dynamo paper and the databases it inspired (Cassandra, Riak, DynamoDB) showed how to build a store that stays available through machine and network failures by giving up some consistency. Designing one covers the core vocabulary of distributed data: partitioning with <Term id="consistent-hashing">consistent hashing</Term>, replication, <Term id="quorum">quorum</Term> reads and writes, conflict resolution, failure detection and repair. It's a favourite deep-dive question because each choice has a clear trade-off.

<Callout type="analogy">
A library that keeps three copies of every book in different branches. To borrow, you check enough branches to be confident you have the latest edition; when a branch was closed during an update, the others leave a note to bring it up to date when it reopens, and a periodic audit compares catalogues to catch anything missed.
</Callout>

## Requirements

**Functional**: `put`, `get`, `delete` by key; values up to ~1 MB; optional <Term id="ttl">TTL</Term>.
**Non-functional**: petabytes of data and millions of operations per second; single-digit-millisecond latency; always writable even during node or zone failures (availability over strict consistency, tunable per request); add and remove nodes without downtime.

## High-level design

<Diagram id="kv-ring" caption="Keys hash onto a ring of virtual nodes; each key is stored on the next N distinct physical nodes clockwise." />

Any node can **coordinate** a request: it hashes the key, finds the replica set, forwards the operation and waits for W (or R) responses. Clients can also be partition-aware and contact a replica directly.

## Partitioning

<Walkthrough id="consistent-hashing" />

<CodeTabs id="hash-ring" title="A consistent hash ring with virtual nodes and replica selection" />

| Scheme | How | Used by |
|---|---|---|
| Consistent hashing with virtual nodes | many tokens per node on a ring; key → next tokens clockwise | Dynamo, Cassandra, Riak |
| Fixed hash slots | `CRC16(key) mod 16384` → slot; slots assigned to nodes and moved whole | Redis Cluster |
| Range partitions that split automatically | sorted key ranges split when large or hot | Bigtable, HBase, DynamoDB (internally), CockroachDB |

Virtual nodes spread each physical node's share across the ring, so adding a node takes a little from many others, and capacity differences can be expressed with more or fewer tokens.

## Replication and consistency

- Each key lives on **N** replicas (e.g. 3), on distinct nodes and ideally distinct zones.
- **Writes** go to all N; the coordinator acknowledges after **W**. **Reads** ask R replicas and return the newest version. W + R > N gives overlap ([Replication](../../databases/replication/)); W = 1/R = 1 is fastest and <Term id="eventual-consistency">eventually consistent</Term>.
- **Versioning**: with concurrent writes to different replicas, versions can conflict. Last-write-wins by timestamp silently drops one; **version vectors** detect concurrency and return siblings for the client (or a <Term id="crdt">CRDT</Term> merge) to resolve.

## Handling failures

| Mechanism | Problem it solves |
|---|---|
| **Gossip** membership + heartbeats | every node learns who's up without a central registry |
| **Sloppy quorum + hinted handoff** | a replica is down: write to the next healthy node with a "hint", deliver when the replica returns |
| **Read repair** | a read sees a stale replica: update it in the background |
| **Anti-entropy with Merkle trees** | replicas compare hash trees of key ranges and sync only differing ranges |
| **Tombstones** | deletes are recorded as markers (with expiry) so they replicate instead of being "resurrected" by stale replicas |

## Storage engine on each node

Writes append to a **commit log** (durability) and an in-memory **memtable**; full memtables flush to immutable sorted **SSTables**; background **compaction** merges them and drops overwritten values and expired tombstones. Reads check the memtable, then SSTables newest-first, skipping most files with **Bloom filters**. This LSM design turns random writes into sequential I/O ([B-trees vs LSM trees](../../databases/indexing/)). TTLs are enforced lazily on read and physically during compaction.

## Trade-offs to discuss

- **AP by default** (always writable, eventual consistency), with per-request knobs towards consistency; strongly consistent operations (compare-and-set) need consensus per key range (Paxos/Raft), at higher latency.
- **<Term id="hot-partition">Hot keys</Term>**: a single key's replicas carry all its load — client-side caching, key splitting, or <Term id="read-replica">read replicas</Term> for hot items.
- **Large values** hurt latency and compaction — store blobs in object storage and keep references.
- <Term id="redis">Redis</Term> Cluster differs from Dynamo: single primary per slot with async replicas (failover can lose acknowledged writes), in-memory storage with optional persistence.

<Pitfalls>

- **`hash(key) % N` partitioning** — almost all keys move when N changes.
- **Replicas on the same rack/zone** — one failure loses all copies.
- **Last-write-wins on data that can't lose updates** (counters, carts) — use CRDTs or conditional writes.
- **Deletes without tombstones** — deleted data reappears from stale replicas.
- **Assuming W + R > N is linearizable** in every failure case.

</Pitfalls>

<KeyTakeaways>

- Consistent hashing or hash slots partition data; virtual nodes balance it.
- N replicas with tunable W/R choose consistency per request.
- Versioning resolves concurrent writes; tombstones make deletes stick.
- Gossip, hinted handoff, read repair and Merkle trees keep replicas converging.
- LSM storage makes each node write-optimised.

</KeyTakeaways>
