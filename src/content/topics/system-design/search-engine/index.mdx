## Why it matters

Search boxes promise relevant results across millions of documents in tens of milliseconds, tolerating typos and partial words. A database `LIKE '%word%'` scans everything; search engines instead build an inverted index from words to documents, rank results with scoring like BM25, and keep the index in sync with the source data. The design covers indexing pipelines, sharding, relevance, autocomplete and permissions.

<Callout type="analogy">
The index at the back of a textbook. To find every page mentioning "photosynthesis" you don't read the whole book; you look up the word and get a list of page numbers. A search engine is that index for millions of documents, updated as they change and sorted by how relevant each page is.
</Callout>

## Requirements

**Functional**: keyword search over titles and bodies with relevance ranking; filters and facets (space, category, author, date); highlighted snippets; autocomplete; typo tolerance; results only from documents the user may see; new and edited documents searchable within seconds.
**Non-functional**: 10 M documents (~20 KB average → ~200 GB of text), ~1 M queries/day with peaks of a few hundred per second; p99 < 200 ms; indexing lag < ~10 s.

## Relevance

- **TF-IDF**: a term matters more if it appears often in this document and rarely across all documents.
- **BM25** (Lucene/Elasticsearch default) adds **saturation** (the tenth occurrence adds little) and **length normalisation** (matches in short documents count more).
- Then business signals: boost title over body, phrase matches, recent or popular documents, the user's own space; tune with relevance judgements and click data, measured offline (NDCG) and online (A/B tests).

## Architecture

<Diagram id="search-architecture" caption="Writes go to the database; an indexer keeps the search cluster in sync; queries go only to the search cluster." />

- **Indexing pipeline**: the document service writes to its database and an outbox; a consumer (or CDC) loads the full document, enriches it (permissions, tags), analyses and upserts it — idempotently, using the document version so out-of-order updates don't regress the index.
- **Reindexing**: build a new index from a snapshot + catch up with the event stream, then switch an alias — no downtime when analysers or mappings change.
- **Sharding**: documents spread across primary shards (size each to ~10–50 GB); every query fans out to all shards and merges top-K. **Replicas** serve reads and survive node loss. Very large multi-tenant corpora can route by tenant to keep queries on few shards.

## Autocomplete, typos and semantics

- **Autocomplete** needs prefix lookups in milliseconds: an edge-n-gram field or completion suggester, or precomputed top suggestions per prefix from query logs (a [trie](../../low-level-design/autocomplete/)) cached in memory.
- **Typos**: fuzzy matching by edit distance (`fuzziness: AUTO`) on longer terms, and "did you mean" from frequent queries.
- **Semantic search**: embed documents and queries as vectors and retrieve by similarity (HNSW indexes in OpenSearch/Elasticsearch or pgvector) to match meaning, not words; combine with BM25 via **hybrid search** (e.g. reciprocal rank fusion) — keyword precision plus semantic recall.

## Permissions

Index each document with its access control (space ids, groups) and add a filter for the user's memberships to every query — filters are cached and cheap. Filtering after retrieval leaks counts and breaks pagination. Permission changes trigger reindexing of affected documents (or store ACLs at a coarser level, like spaces, that change rarely).

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| An index shard is lost | partial results briefly | replicas take over; the shard is rebuilt from a replica or reindexed from the source of truth |
| Indexing lags behind writes | new items missing for a while | the change stream buffers; show 'recently added' from the database if freshness matters |
| A slow query | slow search for one user | query timeouts and limits on expensive features (wildcards, deep pagination) |
| The search cluster is down | search unavailable | degrade to a simple database query for exact matches, or a clear error — the rest of the product works |

<Pitfalls>

- **SQL `LIKE '%…%'` for search** — full scans and no relevance.
- **Different analysis at index and query time** — "Running" never matches "run".
- **Dual writes** from the application to the database and search index — they drift; use an outbox/CDC.
- **Post-filtering for permissions.**
- **One giant shard** (slow recovery) or thousands of tiny ones (overhead).
- **Changing mappings in place** instead of reindexing behind an alias.

</Pitfalls>

<KeyTakeaways>

- Inverted index + consistent analysis + BM25, then business boosts tuned with data.
- Database as source of truth; asynchronous, idempotent, versioned indexing; alias-based reindexing.
- Shards for size, replicas for throughput and availability.
- Permissions as query filters; autocomplete and typo tolerance as separate structures; hybrid search for meaning.

</KeyTakeaways>
