## Requirements

**Functional**: limit requests per key (API key, user, tenant, IP, endpoint) by rules such as "100 per minute" or "10 per second with bursts of 20"; different limits per plan; tell clients when to retry.
**Non-functional**: decisions in about a millisecond (it's on every request); consistent across dozens of instances; highly available — the limiter must not become the outage; 100,000+ decisions per second.

The algorithms themselves (token bucket, windows, leaky bucket) are covered in the [LLD rate limiter](../../low-level-design/rate-limiter/); here the question is how to run one across a fleet.

## Where it sits

| Placement | Pros | Cons |
|---|---|---|
| API gateway / edge (Envoy, NGINX, Spring Cloud Gateway, cloud WAF) | one place, stops abuse before it reaches services | coarse: doesn't know business costs |
| Sidecar / service mesh | per-service policies without code | infrastructure complexity |
| In the service (library + shared store) | business-aware limits (e.g. per tenant per expensive operation) | each service implements it |
| Before calling a partner API (client side) | stay within *their* quota | coordination across your instances |

Most systems combine a coarse edge limit (per IP/API key) with finer in-service limits.

## Shared state and atomicity

With 12 gateway instances each allowing "100/min" locally, a client spread across them gets 1,200/min. The counter must be shared — typically Redis (sub-millisecond, atomic operations, TTLs). The read-check-write must be one atomic step, or two instances both see "99" and both allow. A **Lua script** runs atomically inside Redis; using `redis.call('TIME')` inside it avoids errors from callers' clocks disagreeing.

## Scaling and hot keys

- **Shard by key** across a Redis Cluster; one key's counter lives on one shard.
- A single very hot key (a big tenant's API key) can saturate a shard. Options: **local token batches** — each instance takes, say, 50 tokens at a time from Redis and spends them locally (fewer round trips, slight over-admission); or **approximate local limiting** — each instance enforces `limit ÷ instances` and periodically reconciles.
- Pipelines and connection pooling keep per-request latency low; place Redis in the same zone as the gateways.

## When the limiter's store fails

| Policy | Behaviour | When |
|---|---|---|
| **Fail-open** | allow requests (optionally with a generous local limit) | user-facing APIs where availability matters most |
| **Fail-closed** | reject requests | protecting a fragile, expensive dependency or a strict paid quota |

Either way: tight timeouts (a few milliseconds) on the limiter call, a circuit breaker around it, and alerts.

## Rules, tiers and responses

<CodeTabs id="limiter-rules" title="Rules per plan and endpoint, and the filter that applies them" />

Respond with **429 Too Many Requests**, a `Retry-After` header, and the remaining quota (`X-RateLimit-Limit`/`Remaining`/`Reset`, or the IETF `RateLimit`/`RateLimit-Policy` fields). Clients should back off with jitter.

## Multi-region

A truly global limit needs coordination across regions (expensive, slow). Usual compromises: enforce limits **per region** (divide the quota), or keep regional counters and **asynchronously** share usage, accepting brief over-admission. Strict global quotas (billing) are better computed from usage events afterwards than on the request path.

<Pitfalls>

- **Per-instance in-memory counters** behind a load balancer.
- **Non-atomic check-then-increment** (GET then INCR, or INCR then EXPIRE as separate commands — a crash leaves a key that never expires).
- **Trusting each server's clock** for window boundaries.
- **Limiting only by IP** — NAT and mobile carriers share IPs; attackers rotate them.
- **A slow limiter** without timeouts, adding latency to every request.
- **No visibility** — log and graph 429s per key so legitimate customers hitting limits are noticed.

</Pitfalls>

<KeyTakeaways>

- Global limits need shared, atomic state — Redis + Lua is the common answer.
- Sliding window counter or token bucket: accurate, O(1) per key.
- Choose fail-open or fail-closed deliberately, with millisecond timeouts.
- Handle hot keys with local batching; split quotas per region.
- 429 with Retry-After and quota headers.

</KeyTakeaways>
