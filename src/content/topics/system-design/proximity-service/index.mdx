## Why it matters

"Restaurants near me" sounds like a simple query, but a database can't efficiently answer "within 2 km of this point" with ordinary indexes on latitude and longitude. Proximity services divide the map into cells (geohash, quadtrees, S2 or H3) so nearby places share cell ids and can be found with fast lookups — with care at cell boundaries. Because places change rarely and searches are constant, the design is read-optimised and cache-heavy.

<Callout type="analogy">
Finding a pharmacy using a city map divided into numbered squares. Rather than measuring the distance to every pharmacy in the city, you look in your square and the eight squares around it, then measure only those — and the squares are smaller downtown, where shops are dense.
</Callout>

## Requirements

**Functional**: given a location and radius (or map viewport), return nearby businesses ranked by distance and relevance; view business details; owners add and update businesses (visible within hours is fine).
**Non-functional**: search latency < 200 ms; 100 M daily users; highly available; reads vastly outnumber writes.

## Estimates

| Quantity | Estimate |
|---|---|
| Businesses | 200 M worldwide × ~1 KB details ≈ 200 GB |
| Geo index | id (8 B) + geohash/coordinates (~16 B) ≈ 24 B × 200 M ≈ **5 GB** — fits in memory on every replica |
| Search QPS | 100 M users × 5 searches/day ≈ 5,800/s average, ~20,000/s peak |
| Writes | thousands per hour — negligible |

The index fitting in memory is the key insight: replicate it rather than <Term id="sharding">shard</Term> it.

## Indexing locations

<Walkthrough id="geohash-search" />

<CodeTabs id="geohash" title="Geohash encoding, cell bounds, the 8 neighbours, and a radius search over prefix buckets" />

| Index | Idea | Strengths | Weaknesses |
|---|---|---|---|
| Geohash | Interleaved bits as a string; prefix = containing cell | Simple, works in any key-value store or B-tree (prefix/range scans) | Fixed cell sizes; edge and pole distortions; must query neighbours |
| Quadtree | Split a cell into 4 when it holds > N places | Adapts to density (Manhattan vs desert) | In-memory tree to build and rebalance |
| S2 / H3 | Hierarchical cells on a sphere (squares / hexagons) | Uniform cells, efficient region coverings, H3 neighbours equidistant | Library dependency |
| R-tree (PostGIS) | Bounding-box tree | Arbitrary shapes and polygons, SQL | Single database scaling limits |

Choose precision by radius: cells should be at least as wide as the search radius so 9 cells cover the circle. With a user-chosen radius, start fine and widen (shorter prefix) until enough results are found.

At smaller scale a single PostGIS database (`ST_DWithin` on a GiST index) or <Term id="redis">Redis</Term> GEO is the whole answer; the custom design matters at hundreds of millions of places and tens of thousands of QPS.

## Ranking and results

Distance is rarely the only factor: combine distance, rating, popularity, open-now, price and personalisation, then paginate. Fetch candidate ids from the geo index, details from the cache, and rank in the search service ([Search engine](../search-engine/) covers text relevance when users also type a query).

## Scale and freshness

- **Replicate** the in-memory index to every search node (or a Redis replica set per region); rebuild nightly and apply change events between rebuilds.
- **Cache** popular queries by (geohash cell, filters) — many users in the same area search the same thing.
- **Shard** only if the index or write rate outgrows memory — by region or by geohash prefix.
- **Moving objects** (drivers, couriers) are a different problem: frequent writes, short-lived data — see [Ride-hailing](../ride-hailing/).

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| The geo index service is down | search fails or degrades | replicas serve reads; clients can show cached results for the area |
| A business's details change | stale for minutes | index updates are batched from change events; stale entries are acceptable for this use |
| Heavy load in one city | slower results there | cache popular cells; add read replicas for hot regions |

<Pitfalls>

- **Searching only the user's cell** — misses nearby results across boundaries.
- **Treating cells as distance** — always filter by exact distance.
- **Sharding a 5 GB index** that could simply be replicated.
- **One precision for all densities** — too many candidates downtown, too few in rural areas (quadtrees or adaptive radius help).
- **<Term id="coupling">Coupling</Term> business CRUD and search** in one service and database.

</Pitfalls>

<KeyTakeaways>

- Geo indexes turn "near" into cell lookups: geohash, quadtree, S2/H3 or R-trees.
- Search the user's cell plus neighbours, then filter and rank by exact distance and relevance.
- Read-heavy, small index: replicate in memory, cache popular cells, update asynchronously.
- Use Redis GEO or PostGIS until scale demands a custom service.

</KeyTakeaways>
