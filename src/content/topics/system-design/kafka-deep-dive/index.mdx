## Why it matters

Kafka is the default backbone for events between services, change data capture, and stream processing. It's easy to get a hello-world working and easy to ship something that loses messages on broker failure, processes payments twice after a rebalance, or stalls a whole partition on one bad message. Interviewers probe exactly these details: ordering, delivery guarantees, consumer groups, and what happens when things crash.

## The architecture

<Diagram id="kafka-architecture" caption="Partitions are replicated across brokers; each has one leader that producers write to and consumers read from." />

| Term | Meaning |
|---|---|
| Broker | a Kafka server storing partition replicas |
| Topic / partition | named stream / one ordered log of it; the unit of parallelism and ordering |
| Offset | position of a record in a partition |
| Leader / followers | one replica serves reads and writes; followers copy it |
| ISR | in-sync replicas: followers that are caught up |
| Controller (KRaft) | Raft-based metadata quorum managing brokers, topics and leadership (ZooKeeper removed in Kafka 4.0) |
| Consumer group | consumers sharing a subscription; each partition assigned to one member |

## Producers

<CodeTabs id="kafka-producer" title="A durable, idempotent producer — Java, Node, Python" />

- **Key → partition** (`hash(key) % partitions`): same key, same partition, same order. A `null` key spreads records but gives no ordering. Changing the partition count remaps keys.
- **`acks=all` + `min.insync.replicas=2`** (with replication factor 3): a write is acknowledged only when at least two replicas have it — one broker can fail without losing acknowledged data. `acks=1` is faster but loses data if the leader dies before followers copy it.
- **Idempotence** (`enable.idempotence=true`, default since 3.0): the broker de-duplicates retried batches using producer id + sequence numbers, so retries don't duplicate or reorder.
- **Batching**: `linger.ms` (wait a few ms to fill batches) and `batch.size`, plus `compression.type=lz4` or `zstd`, trade a little latency for much higher throughput.
- **Transactions** (`transactional.id`) write to several partitions atomically and commit consumer offsets in the same transaction — exactly-once for Kafka-to-Kafka pipelines (read-process-write), not for external side effects.

## Consumers and groups

<Walkthrough id="consumer-group" />

- Partitions are divided among group members; adding consumers beyond the partition count leaves them idle. Choose partition counts for peak parallelism (increasing later is possible but remaps keys).
- **Offsets** are committed to the internal `__consumer_offsets` topic. On restart or reassignment, consumption resumes from the last committed offset — anything processed but not committed is **redelivered**.
- **Auto-commit** commits on a timer, regardless of whether processing finished: on a crash it can both redeliver *and* skip records. Commit after processing (Spring Kafka's default `AckMode.BATCH`, or manual acks).
- **Rebalances** happen when members join/leave, crash or exceed `max.poll.interval.ms` between polls. Use cooperative-sticky assignment (or the KIP-848 protocol in Kafka 4) to move only affected partitions, keep processing per poll bounded, and use static membership (`group.instance.id`) for rolling restarts.
- **Lag** (latest offset − committed offset) is the key health metric; alert on it and scale on it.

## Ordering, retries and poison messages

- Ordering holds per partition **only if** you process records of a partition sequentially. Parallel processing within a partition (thread pools) breaks it unless you partition work by key.
- A message that always fails ("poison pill") blocks its partition if retried forever. Retry a few times with backoff, then publish it to a **dead-letter topic** with the error, and move on; alert and reprocess later.
- **Non-blocking retries** (retry topics with delays) keep the partition moving but give up strict ordering for the retried records.

## Delivery semantics end to end

<CodeTabs id="kafka-idempotent-consumer" title="Exactly-once effects: dedupe in the same database transaction" />

| Pipeline | How to get "exactly-once" results |
|---|---|
| Kafka → Kafka (stream processing) | Kafka transactions / Kafka Streams `exactly_once_v2` |
| Kafka → database | idempotent writes: processed-id table or upserts in the same transaction as the effect |
| Kafka → external API (payments, email) | idempotency keys on the external call; record the outcome |

## Retention and compaction

- **Delete** policy: keep data for `retention.ms` (e.g. 7 days) or until `retention.bytes`, then delete old segments.
- **Compact** policy: keep at least the latest record per key forever (and tombstones for deletes) — a table-like changelog, ideal for "current state of each entity" and for rebuilding caches.
- Tiered storage moves old segments to object storage for long retention at lower cost.

## Sizing and tuning

| Knob | Effect |
|---|---|
| Partitions | parallelism and throughput; too many increases metadata, open files and recovery time |
| `replication.factor=3`, `min.insync.replicas=2` | survive one broker failure without losing acknowledged writes |
| `linger.ms`, `batch.size`, compression | producer throughput vs latency |
| `fetch.min.bytes`, `max.poll.records` | consumer batch size |
| `max.poll.interval.ms` | how long processing a batch may take before the member is considered dead |
| Consumer concurrency | up to the number of partitions assigned |

<Pitfalls>

- **`acks=1` or `min.insync.replicas=1`** for data you can't lose.
- **Auto-commit** with slow or failing processing — lost and duplicated records.
- **Non-idempotent consumers** — rebalances and crashes cause duplicates.
- **Retrying a poison message forever** — the partition stops.
- **Processing a partition's records in parallel** and expecting order.
- **Too few partitions** (can't scale consumers) or far too many (slow recovery, overhead).
- **Changing the partition count** of a keyed topic without planning — keys move, ordering breaks across the change.
- **Long work inside the poll loop** exceeding `max.poll.interval.ms` → rebalance storms.

</Pitfalls>

<KeyTakeaways>

- Partitions = ordering + parallelism; keys choose partitions.
- `acks=all`, RF 3, min ISR 2, idempotent producer for durability.
- Commit after processing, make consumers idempotent, dead-letter poison messages.
- Watch lag and rebalances; size partitions for peak parallelism.
- Retention for history, compaction for latest-state-per-key.

</KeyTakeaways>
