## Why it matters

A paste or snippet-sharing service is mostly reads: content is written once and then viewed many times, sometimes by millions of people when a link goes viral. That makes it a clean design exercise in separating metadata from content, generating short unique ids, serving reads from a <Term id="cdn">CDN</Term> and object storage rather than a database, and expiring data on schedule — the same shape as image hosting, file sharing links and many internal artifact stores.

<Callout type="analogy">
A public notice board with a numbered key for each notice. Posting a notice takes a minute; reading it takes seconds, and popular notices get photocopied to boards all over town (the CDN). Notices with an expiry date are taken down by a nightly sweep.
</Callout>

## Requirements

**Functional**: create a paste (text up to e.g. 10 MB, optional language, expiry, visibility public/unlisted/private, optional password or burn-after-reading); view by link; raw download; delete by owner.
**Non-functional**: ~10 M new pastes/day, ~100 M reads/day with sharp spikes on viral pastes; durable until expiry; reads in tens of milliseconds worldwide.

## Estimates

Writes ≈ 120/s; reads ≈ 1,200/s average but a single viral paste can add thousands per second. Average paste ~10 KB → 100 GB/day of content → ~36 TB/year — object storage territory; metadata rows (~300 B) → ~1 TB/year, fine for a relational store.

## API

```http
POST   /api/pastes            { "content": "...", "language": "java", "expiresIn": "P7D", "visibility": "unlisted" }
→ 201  { "id": "Xk29fQa", "url": "https://paste.example/Xk29fQa" }
GET    /{id}                  → HTML view (syntax highlighting in the browser)
GET    /raw/{id}              → text/plain, cacheable
DELETE /api/pastes/{id}
```

Large uploads can go straight to object storage with a **presigned URL** limited in size and time, so app servers never stream megabytes.

## Deep dives

**Viral pastes.** Because content never changes, public responses carry `Cache-Control: public, max-age=…` (capped at the time to expiry) and the CDN absorbs the spike: the origin sees roughly one request per edge per <Term id="ttl">TTL</Term>. Behind it, a <Term id="redis">Redis</Term> cache keeps hot pastes' content (size-capped — megabyte values belong in the object store, not Redis).

**Expiry.** The read path checks `expires_at` and returns 404/410 even if cleanup hasn't run; object-store lifecycle rules or a batch job delete expired content; metadata TTL (DynamoDB TTL) or a periodic `DELETE … WHERE expires_at < now()` in batches; cache TTLs never exceed the remaining lifetime.

**Private and protected pastes.** Never cache them publicly: `Cache-Control: private, no-store`, authorisation on every read, content served through short-lived signed URLs. Passwords are hashed (bcrypt/argon2) and checked server-side; burn-after-reading uses an atomic "mark as read" (conditional update) so two concurrent readers can't both see it.

**Deduplication (optional).** Store content under its SHA-256 hash; many identical pastes share one object. Saves storage for repeated content; deletion then needs reference counting.

**Abuse.** Per-IP and per-account rate limits on creation ([Rate limiting](../distributed-rate-limiter/)), size limits enforced at the edge and in presigned policies, scanning for leaked credentials and malware, and a takedown path.

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| A paste goes viral | nothing | content is immutable and served from the CDN; the origin sees a tiny fraction of reads |
| Object storage is unavailable | new pastes fail, old ones still load | CDN keeps serving cached content; writes return a clear error and clients retry |
| The metadata database is down | creating fails | reads by id can come from cache/CDN; writes fail fast |
| Expiry job falls behind | expired pastes visible briefly | reads check the expiry time before serving, regardless of cleanup |

<Pitfalls>

- **Large blobs in the database or Redis** — bloats backups and memory; use object storage.
- **Public caching of private pastes.**
- **Cache TTLs longer than the paste's lifetime** — expired pastes keep being served.
- **Burn-after-reading with a read-then-delete race.**
- **Unbounded uploads through app servers.**

</Pitfalls>

<KeyTakeaways>

- Immutable content + CDN = cheap reads even for viral pastes.
- Metadata in a database, bytes in object storage, presigned uploads for large content.
- Expiry enforced on read; cleanup is lazy and batched.
- Private content: no shared caching, signed URLs, server-side checks.

</KeyTakeaways>
