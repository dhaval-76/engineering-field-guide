## Why it matters

Wikis, document editors and code hosts all promise that you can see every past version, compare any two, and restore one. Storing full copies of large documents on every save wastes storage; storing only deltas makes old versions slow to rebuild. The design balances storage, read speed for old versions and features like drafts and merges — and it's a good interview test of content-addressed storage, deduplication and diffing.

<Callout type="analogy">
A legal contract with a change log. Instead of photocopying the whole contract on every edit, the clerk records "page 3, clause 2 changed", and every tenth revision keeps a full clean copy, so reconstructing any version needs at most a few pages of changes applied to the nearest clean copy.
</Callout>

## Requirements

**Functional**: every save creates a version (author, time, message); list a page's history; view any version; diff two versions; restore an old version; optionally draft branches merged back with conflict detection; "blame" (who wrote this paragraph).
**Non-functional**: 10 M pages, 100 M+ versions; history pages load in < 300 ms; any version reconstructed in < 500 ms; storage cost far below "full copy per version".

## Estimates

Average page 20 KB × 100 M versions = 2 TB as full copies — affordable, but large pages edited thousands of times (and collaborative autosave) make it 10–100× worse. Most edits change a few lines, so deltas are typically 1–5% of the page.

## Data model

<Diagram id="version-graph" caption="Versions form a graph of immutable snapshots; pages and drafts are pointers into it; content is stored once per unique hash." />

<CodeTabs id="version-model" title="Versions, content-addressed blobs and a commit" />

- **Blob**: content stored under `sha256(content)` (or chunks of it). Saving unchanged content, or restoring an old version, stores nothing new.
- **Version**: id, page, parent(s), blob hash, author, time, message — immutable.
- **Head pointer**: the page's current version; a **draft** is another pointer, created in O(1).
- Writes use compare-and-set on the head (`UPDATE pages SET head = new WHERE id = ? AND head = expected`) so two saves can't silently fork history.

## Storage: deltas and snapshots

<Walkthrough id="delta-chain" />

Store a **full snapshot** every k versions and **deltas** in between; reconstructing any version costs at most k−1 delta applications. Git does a similar thing (packfiles with delta chains). Large binary attachments use content-defined chunking so small changes don't duplicate whole files.

## Diff, restore, blame

- **Diff**: Myers diff over lines, or over blocks/paragraphs for rich documents, then within changed blocks; cache diffs by `(hashA, hashB)` since content hashes never change meaning.
- **Restore**: create a new version whose content is the old blob — history is never rewritten.
- **Blame**: walk back through versions diffing each against its parent and attributing surviving lines; cache results per version.

## Drafts and merging

<CodeTabs id="three-way-merge" title="Three-way merge of block-structured documents" />

Find the **common ancestor** of the draft and the current head; for each block, compare both sides to the ancestor: changed on one side → take it; changed identically → take it; changed differently → **conflict** shown to the user, whose resolution becomes a merge version with two parents.

## Collaboration and retention

Real-time editors ([Collaborative editing](../realtime-collaboration/)) produce a stream of tiny operations; version history groups them into meaningful versions (per editing session or every few minutes of activity) and lets users name versions. Retention policies thin old autosaves (keep hourly, then daily) while keeping named versions; deleted pages' blobs are garbage-collected when no version references them.

## When things fail

Interviewers almost always ask "what happens when X goes down?". Decide the degraded behaviour in advance:

| What fails | What users see | What the design does |
|---|---|---|
| Blob storage is unavailable | can't open old versions | the current version is cached separately; history loads when storage recovers; saves are queued or rejected clearly |
| A save is interrupted halfway | nothing | write the blob first, then the version record in one transaction — a version never points to a missing blob |
| Two people save the same base version | a merge or a conflict prompt | compare base version ids; three-way merge or keep both as drafts |
| A delta chain becomes very long | slow history views | periodic full snapshots bound how many deltas must be applied |

<Pitfalls>

- **Mutable versions** or "restore" that overwrites history.
- **Full copies of large documents** for every autosave.
- **Unbounded delta chains** — slow reconstruction of old versions.
- **Line-based merges for rich documents** — merge by blocks/structure.
- **Racing saves** without compare-and-set on the head.

</Pitfalls>

<KeyTakeaways>

- Immutable versions in a DAG; heads and drafts are pointers.
- Content addressing deduplicates; deltas + periodic snapshots keep storage small and reads bounded.
- Diffs by blocks then lines, cached by content hash.
- Three-way merges against the common ancestor; conflicts explicit.

</KeyTakeaways>
