## Why it matters

Once a product has more than a handful of services, every client would otherwise need to know where each one lives, how to authenticate to it and how to cope when it's slow. An API gateway is the single front door that handles those cross-cutting jobs once — TLS, authentication, routing, rate limits, retries — so services can focus on business logic. Because **every** request passes through it, it has to add almost no latency, stay stateless so it can scale out, and never become the single point that takes the whole product down.

<Callout type="analogy">
A hotel reception desk. Guests don't wander the corridors looking for housekeeping, the restaurant or the spa — they ask at one desk, which checks their room key, knows where every service is, calls ahead, and turns people away politely when a venue is full. The desk must be quick, or the whole lobby queues.
</Callout>

## Requirements

**Functional**: route external requests to the right service by host, path and method; authenticate callers (user tokens, API keys) and pass identity downstream; enforce rate limits and quotas; reject oversized or malformed requests; support versioned APIs and canary releases; log and trace every request.
**Non-functional**: tens of thousands of requests per second; under ~5 ms added latency; higher availability than any service behind it; configuration changes without redeploys.

## High-level design

<Diagram id="gateway-architecture" caption="A gateway request pipeline: cheap checks first, then routing to a healthy upstream with timeouts and a circuit breaker." />

| Step | Work | Cost |
|---|---|---|
| TLS termination | decrypt, HTTP/2 or HTTP/3 | CPU; offload or reuse sessions |
| Request limits | max body/header size, allowed methods, CORS | trivial |
| Authentication | verify JWT signature against cached JWKS keys, or look up an API key (cached) | sub-ms, no network call |
| Rate limiting | one Redis call per request ([distributed limiter](../distributed-rate-limiter/)) | ~1 ms |
| Routing | match route table (host + longest path prefix + method), choose a healthy instance | microseconds |
| Forwarding | connection pools to upstreams, per-route timeout, retries for idempotent methods, circuit breaker | upstream latency |
| Observability | trace id, access log (async), metrics per route/status | asynchronous |

## Deep dives

**Authentication at the edge.** Validate signature, issuer, audience and expiry locally using public keys from the identity provider's JWKS endpoint (cached and refreshed in the background). Forward identity to services as a verified token or signed headers, and have services still verify — the gateway is not the only line of defence. Revocation is handled with short-lived tokens plus a small deny-list or per-user "valid after" timestamp ([Auth at scale](../auth-at-scale/)).

**Availability.** Gateways are stateless: run many instances across zones behind a DNS/L4 load balancer, with health checks. Route configuration is versioned and pushed (or polled) — a bad config must be rejected or rolled back quickly, because it affects every service.

**Latency.** No synchronous calls to slow systems in the pipeline; connection pooling and keep-alive to upstreams; async access logs; avoid body parsing unless a route needs transformation.

**Releases.** Weighted routes (95% v1, 5% v2) or header-based routing (`X-Canary: true`) enable canaries and blue-green switches at the edge.

**Gateway vs BFF vs service mesh.** The gateway handles north-south traffic (clients → services). A **backend for frontend** per client type (web, mobile) aggregates and reshapes data for one UI. A **service mesh** handles east-west traffic (service → service): mTLS, retries, traffic splitting via sidecars or ambient proxies. Putting aggregation logic for every screen into the shared gateway creates a monolith that every team must change.

<Pitfalls>

- **Business logic in the gateway** — every change touches a shared, critical component.
- **Calling the auth service on every request** instead of verifying tokens locally.
- **Retrying non-idempotent requests** at the gateway (duplicate orders).
- **One timeout for all routes** — slow report endpoints and fast lookups need different values.
- **A single gateway instance or zone.**
- **Unreviewed route changes** pushed straight to production.

</Pitfalls>

<KeyTakeaways>

- Centralise cross-cutting concerns; keep the gateway thin, stateless and fast.
- Local JWT verification, Redis-backed limits, per-route timeouts and circuit breakers.
- Many instances across zones; versioned, validated configuration.
- BFFs for client-specific aggregation, a mesh for service-to-service concerns.

</KeyTakeaways>
