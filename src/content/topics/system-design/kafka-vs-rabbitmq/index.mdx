## Why it matters

"Put it on a queue" is a common answer in system design, but there are two quite different things it can mean. Sending a thumbnail job to exactly one of ten workers is a different problem from announcing "order placed" to inventory, email, analytics and a service that doesn't exist yet. Picking a tool built for the wrong shape leads to awkward workarounds: fan-out bolted onto a queue, or per-message retries and priorities bolted onto a log.

<Callout type="analogy">
A queue is a pile of work orders on a counter: whichever worker is free takes the top one, and once done, it's gone. A log is a newspaper archive: every subscriber reads every edition at their own pace, a new subscriber can start from last year's issues, and reading doesn't remove anything.
</Callout>

## Side by side

| Aspect | Kafka (log) | RabbitMQ (queue broker) |
|---|---|---|
| Unit | topic → partitions (ordered, append-only) | exchange → bindings → queues |
| After consumption | message stays until retention/compaction | removed once acknowledged |
| Fan-out | each consumer group reads everything | one queue per subscriber, bound to an exchange |
| Parallelism | partitions; one consumer per partition per group | competing consumers on a queue, prefetch limits |
| Ordering | per partition (per key) | per queue (lost with competing consumers or redelivery) |
| Replay / new consumers from history | yes — reset offsets | no for queues; yes with RabbitMQ **streams** |
| Routing | by topic and key | direct, topic (wildcards), fanout, headers exchanges |
| Per-message features | limited: retries via retry topics and DLT | acks/nacks per message, TTL, priorities, dead-letter exchanges, delayed delivery |
| Throughput | very high (sequential disk, batching) | high, lower per node; quorum queues trade some speed for safety |
| Consumer model | pull | push with prefetch |

Recent changes worth knowing: Kafka 4.0 runs without ZooKeeper (KRaft) and has a faster consumer-group protocol, and is adding **share groups** for queue-like consumption; RabbitMQ 4 favours **quorum queues** (Raft-replicated) and offers **streams** with Kafka-like replay.

## Delivery guarantees

| Guarantee | How | Risk |
|---|---|---|
| At-most-once | acknowledge/commit before processing | crash → message lost |
| **At-least-once** (default) | acknowledge/commit after processing | crash → message redelivered → duplicates |
| Effectively exactly-once | at-least-once + idempotent consumer, or Kafka transactions for Kafka-to-Kafka pipelines | design effort |

"Exactly once" end to end, including side effects like charging a card or sending an email, comes from **idempotent processing** — remembering what you've handled ([Idempotency](../../backend/idempotency/)).

## Choosing

| Need | Good fit |
|---|---|
| Many independent consumers of the same events; adding consumers later; replay; event sourcing; stream processing; very high volume | Kafka (or Kinesis, Pulsar, Redpanda) |
| Distributing jobs to workers with per-message retries, priorities, delays, complex routing, request/reply | RabbitMQ (or SQS, ActiveMQ) |
| Managed, minimal operations on AWS | SQS (queue), SNS → SQS (fan-out), Kinesis or MSK (log) |
| Simple background jobs in an app already using Postgres or Redis | a database table with `SKIP LOCKED`, or Redis Streams |
| Lightweight pub/sub and request/reply at the edge | NATS (JetStream for persistence) |

Many systems use both: Kafka for domain events between services, and a queue (or a table) for each service's internal job processing.

<Pitfalls>

- **Using a queue for fan-out to many services** — every new consumer needs a new queue and binding, and late joiners get no history.
- **Using Kafka as a job queue with per-message retries and priorities** — partitions block on a poison message unless you build retry topics.
- **Assuming exactly-once** — design for duplicates.
- **Null keys in Kafka when order matters** — related events land on different partitions.
- **No dead-letter handling** — one bad message retried forever.
- **Unbounded queues** with no alerting on depth or consumer lag.

</Pitfalls>

<KeyTakeaways>

- Queue = work distribution, message gone after ack. Log = durable stream, many readers, replay.
- Kafka for events, fan-out, replay and volume; RabbitMQ/SQS for task queues with routing and per-message control.
- At-least-once is the norm; idempotent consumers make it safe.

</KeyTakeaways>
