## Why it matters

Design patterns give names to shapes of code that keep recurring. Saying "wrap the client in a retrying decorator" or "orders are a state machine" communicates a whole design in a sentence, and the pattern carries known trade-offs with it.

They come from the 1994 *Gang of Four* book, which catalogued 23 patterns for object-oriented languages. Some are now built into languages (Iterator → `for…of`, Strategy → lambdas); a handful dominate day-to-day backend work and LLD interviews.

<Callout type="analogy">
A carpenter's vocabulary. "Dovetail joint" names a design that solves a specific problem — two boards that must not pull apart — and every carpenter knows its strengths and costs. Nobody uses a dovetail where two nails would do. Pattern names work the same way: a shared, precise word for a proven solution, used only when the problem calls for it.
</Callout>

<Diagram id="pattern-families" caption="The Gang of Four grouped patterns by what they help with: creating objects, combining them, or dividing behaviour between them." />

<Callout type="warning" title="Problem first">
Patterns are answers. Reaching for one before you have the question produces needless interfaces, factories for single classes and singletons everywhere. Describe the force first — "this varies", "this must be undoable", "callers shouldn't know about this vendor" — then name the pattern that resolves it.
</Callout>

## Four more you'll meet often

### Command

Turn an action into an object with `execute()` (and often `undo()`). Once actions are objects you can put them on a stack for undo/redo, in a queue for later execution, or in a log to replay.

<CodeTabs id="patterns-command" title="Undo/redo with command objects" />

### Chain of Responsibility

A request passes through a sequence of handlers; each can handle it, reject it, or pass it on. This is how HTTP middleware, servlet filters and Spring Security's filter chain work.

<CodeTabs id="patterns-chain" title="Authentication and rate limiting as a handler chain" />

### Template Method

A base class defines the fixed sequence of steps in an algorithm and lets subclasses supply some of the steps. Frameworks use it heavily (`JdbcTemplate`, test lifecycle hooks). Composition (passing in strategies) is often a more flexible alternative.

<CodeTabs id="patterns-template" title="An import pipeline with fixed steps" />

### Composite

Individual objects and groups of objects share one interface, so you can treat a tree uniformly — file systems, UI component trees, organisation charts, nested discount bundles.

## The rest of the catalogue, briefly

| Pattern | Family | One-line idea | Where you'll see it |
|---|---|---|---|
| Abstract Factory | Creational | Create families of matching objects | Cloud/infra abstraction, UI themes |
| Prototype | Creational | Create by copying an existing object | `clone()`, copying configured templates |
| Bridge | Structural | Separate an abstraction from its implementation so both vary | JDBC API ↔ drivers |
| Flyweight | Structural | Share immutable parts of many small objects | `Integer.valueOf` cache, glyphs in editors |
| Iterator | Behavioural | Traverse without exposing internals | Built into every language's `for` loop |
| Mediator | Behavioural | Objects talk via a central coordinator | Chat rooms, UI dialogs, air-traffic control |
| Memento | Behavioural | Capture and restore an object's state | Undo via snapshots |
| Visitor | Behavioural | Add operations over a fixed set of types | Compilers/AST processing; Java `switch` on sealed types often replaces it |
| Interpreter | Behavioural | Represent a small language as objects | Rule engines, expression evaluators |

## Patterns beyond the classic catalogue

Backend systems lean on patterns that came after the GoF book; each has its own topic in this guide:

- **<Term id="dependency-injection">Dependency Injection</Term> / Inversion of Control** — the container builds and wires objects (Spring).
- **Repository** — a collection-like interface over persistence.
- **<Term id="circuit-breaker">Circuit breaker</Term>, retry, <Term id="bulkhead">bulkhead</Term>** — resilience patterns for remote calls.
- **<Term id="saga">Saga</Term>, <Term id="outbox">outbox</Term>, <Term id="cqrs">CQRS</Term>, <Term id="event-sourcing">event sourcing</Term>** — patterns for consistency across services.

<Pitfalls>

- **Pattern first, problem second** — interfaces with one implementation, factories that build one class, abstractions nobody needs.
- **Singletons as global variables** — hidden dependencies and tests that leak state into each other; let the DI container own lifetimes.
- **Deep decorator or chain stacks** that nobody can follow in a stack trace — keep them short and named.
- **Observer without ownership** — listeners that are never unsubscribed leak memory and fire on dead objects.
- **Re-implementing what the language already has** — a hand-written Iterator or Strategy class where a `for` loop or a lambda is clearer.

</Pitfalls>

<KeyTakeaways>

- Patterns are shared names for recurring solutions; start from the problem, not the pattern.
- Creational = making objects, structural = composing them, behavioural = how they collaborate.
- The everyday set: Factory, Builder, Strategy, State, Observer, Decorator, Adapter, Facade, Proxy, Command, Chain of Responsibility, Template Method, Composite.
- Modern language features (lambdas, sealed types, iterators) make several patterns lighter or built-in.

</KeyTakeaways>
