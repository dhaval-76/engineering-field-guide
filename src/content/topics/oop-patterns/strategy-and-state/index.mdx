## Why it matters

Two smells show up in almost every codebase:

- `if (option == STANDARD) … else if (option == EXPRESS) …` — **different ways to do the same job**.
- `if (status == PLACED) … else if (status == PAID) …` repeated in every method of `Order` — **behaviour that depends on a stage in a lifecycle**.

Both grow with every requirement and both are where bugs hide ("you could cancel a delivered order"). Strategy and State turn each branch into its own small class, so the variation is explicit and new cases are additions, not edits.

<Callout type="analogy">
**Strategy** is a navigation app's route choice: fastest, shortest, avoid tolls. Same trip, swappable algorithm — and *you* choose it. **State** is a traffic light: what it does next depends on which colour it is now, and *it* moves itself from green to amber to red.
</Callout>

## Strategy

A **context** (checkout, scheduler, HTTP client) holds a reference to a **strategy interface** and delegates one decision to it. The client — or a factory — chooses which strategy to use, often at runtime.

## State

An object's behaviour depends on its current state, and calling an action can move it to a new state. Instead of a `switch (status)` in every method, each state is an object that implements the actions legal in that state and returns (or sets) the next state.

Two implementations, both valid:

- **State objects** (Java tab): each state class owns its behaviour. Best when states have rich, different behaviour — what's displayed, what's validated, what side effects happen.
- **Transition table** (JavaScript/Python tabs): a map of `state → action → next state`. Best when states mostly differ in *which transitions are allowed*. Easy to read, test and even render as a diagram.

A vending machine is the classic interview example, because each button means something different depending on whether money has been inserted:

## Strategy vs State

They look identical in a class diagram — an interface with several implementations, held by a context. The difference is **who chooses** and **whether it changes over time**.

| Aspect | Strategy | State |
|---|---|---|
| Chosen by | The client/configuration | The state objects themselves (transitions) |
| Changes during the object's life | Rarely (set once per operation) | Constantly, as events happen |
| Implementations know about each other | No — they're independent | Yes — a state knows its successors |
| Answers | *How* to do X | *What* X does right now |
| Example | Pricing algorithm for this customer | Order is Placed → Paid → Shipped |

They combine well: an order's `Paid` state might use a `RefundPolicy` strategy when cancelled.

</Callout>

## In production

<Pitfalls>

- **State stored as a free-form string.** Use an enum and a single place that validates transitions; never let code set `status` directly.
- **Races on transitions.** Two requests can both read `PAID` and both apply `cancel` and `ship`. Make the transition atomic in the database: `UPDATE orders SET status='SHIPPED' WHERE id=? AND status='PAID'` and check the row count, or use a version column.
- **A class per strategy for a one-line rule.** A lambda or map entry is enough; promote to a class when it gains dependencies or tests.
- **Strategy selection logic spread around.** Keep "which strategy?" in one factory/registry.
- **Forgetting the audit trail.** Real lifecycles need history — store transitions (from, to, who, when) as well as the current state.

</Pitfalls>

<KeyTakeaways>

- Strategy: interchangeable algorithms, chosen from outside. State: behaviour that changes with internal state, transitions decided inside.
- Both replace type/status switches with polymorphism and make new cases additive.
- Use lambdas for one-method strategies and transition tables for simple state machines.
- Make state transitions explicit, validated and atomic.

</KeyTakeaways>
