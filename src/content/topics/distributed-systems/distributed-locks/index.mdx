## Why it matters

`synchronized` protects data inside one process. With ten instances of a service, a scheduled job runs ten times, and two requests for the same account can run on different machines. Distributed locks look like the fix, but they fail in subtle ways: processes pause, clocks drift, networks partition. Interviewers like this topic because naive answers ("use Redis SETNX") hide real bugs.

<Callout type="analogy">
A meeting-room booking with a time limit. You book the room until 3 pm; if you forget to leave, the next team can take it at 3. That's what stops a no-show from blocking the room forever — and also why, if your meeting overruns without you noticing, you suddenly share the room with someone else. A fencing token is the receptionist checking the latest booking number before letting anyone use the projector.
</Callout>

## Do you need a lock?

| Problem | Often better than a lock |
|---|---|
| Two requests update the same row | Optimistic concurrency (version column), `UPDATE … WHERE` conditions, `SELECT … FOR UPDATE` in one DB |
| Avoid processing a message twice | Idempotency keys / inbox table ([Idempotency](../../backend/idempotency/)) |
| Only one row per business key | Unique constraint |
| All updates for one entity in order | Partition by entity id (Kafka key) so one consumer owns it |
| A cron job should run once | A scheduler with a lease (ShedLock, Quartz cluster) — still a lock, but packaged |

## Lease-based locks in Redis

<CodeTabs id="dlock-redis" title="Acquire with a unique token and TTL; release and extend only if the token still matches" />

Rules that matter:

- **Unique token per acquisition**, and release with a compare-and-delete script — otherwise you can delete a lock that expired and was taken by someone else.
- **TTL longer than the work**, or extend it with a heartbeat while working; stop working if an extend fails.
- **Single Redis node** = single point of failure; with replication, a failover can lose a just-acquired lock (replication is asynchronous).

## Fencing tokens

<Walkthrough id="fencing-tokens" />

<CodeTabs id="fencing" title="A lease service issuing increasing tokens, and storage that rejects stale ones" />

Any lease-based lock can have two holders at once from the holders' point of view — expiry is decided by the lock service's clock, and a paused client can't notice. The only robust fix is for the **resource** to reject stale holders: pass the token with every write and keep the highest seen. Databases can do this with a `WHERE token >= :token` condition; etcd and ZooKeeper provide naturally increasing revision/sequence numbers to use as tokens.

## Choosing an implementation

| Option | Safety | Notes |
|---|---|---|
| Redis single node, `SET NX PX` | Efficiency only | Simple, fast; lost on failover |
| Redlock (5 independent Redis nodes, majority) | Debated | Relies on bounded clock drift and pauses; criticised (Kleppmann) for lacking fencing — don't use it for correctness |
| Database row lock / `FOR UPDATE` | Strong within one DB | Best when the protected data is in that database anyway |
| Postgres advisory lock | Strong while the session/transaction lives | Named locks without a table; tied to a connection |
| etcd / ZooKeeper / Consul | Strong (consensus) | Leases with keep-alives, watches, revision numbers usable as fencing tokens |

<CodeTabs id="db-locks" title="Database-backed options: row locks, advisory locks, and a lease table with a fencing token" />

<Steps>

1. **Classify**: if two holders would only waste work, a Redis lease is fine. If they'd corrupt data or double-charge, you need fencing and a strongly consistent lock — or a design without a lock.
2. **Bound the work** by the lease: extend with heartbeats and abort when you lose the lease.
3. **Make the work idempotent** anyway — locks reduce duplicates, they don't eliminate them.
4. **Monitor** acquisition latency, contention and lease losses.

</Steps>

<Pitfalls>

- **`DEL` to release** without checking the token — removes someone else's lock.
- **`SETNX` then `EXPIRE` as two commands** — a crash in between leaves a lock that never expires. Use `SET … NX PX`.
- **TTL shorter than the work** with no extension.
- **Trusting a lease for correctness** without fencing.
- **Locking across a network call to a slow service** — contention and long holds.
- **Reaching for a lock** when a unique constraint, conditional update or partitioning solves it.

</Pitfalls>

<KeyTakeaways>

- Prefer designs that don't need locks: idempotency, optimistic concurrency, constraints, single-owner partitions.
- Distributed locks are leases; leases can be lost silently.
- Owner-checked release, TTL plus heartbeat, and fencing tokens checked by the resource.
- Redis for efficiency locks; databases or consensus systems for correctness.

</KeyTakeaways>
