## Why it matters

Distance is latency, and no amount of server tuning beats the speed of light. A CDN moves content close to users, absorbs most traffic before it reaches your servers, and doubles as a shield against spikes and attacks. For media, downloads and global products it's the single largest performance and cost lever — and it appears in nearly every system design ([Video streaming](../../system-design/video-streaming/), [File storage](../../system-design/file-storage/)).

<Callout type="analogy">
A publisher printing books in one city versus keeping copies in every neighbourhood library. Readers get a local copy in minutes instead of waiting for shipping, and the publisher only sends new editions to the libraries — not a copy to every reader.
</Callout>

## How it works

<Diagram id="cdn-tiers" caption="Users reach the nearest edge PoP; edge misses go to a regional shield, so the origin sees roughly one request per object per expiry rather than one per PoP." />

<Steps>

1. **Routing**: anycast (the same IP announced from every PoP; BGP picks the nearest) or GeoDNS returns the nearest healthy PoP.
2. **Cache key**: usually scheme + host + path + selected query parameters and headers (`Vary`). Every extra variation (cookies, tracking parameters) fragments the cache — normalise keys.
3. **Freshness**: `Cache-Control` from the origin decides how long edges and browsers keep a response.
4. **Tiered caching**: misses go to a shield PoP, collapsing simultaneous requests ("request coalescing") so the origin isn't stampeded.
5. **Edge features**: <Term id="tls">TLS</Term> termination with <Term id="http2">HTTP/2</Term>–3, compression, image resizing, WAF rules, bot and DDoS mitigation, and small edge functions (redirects, A/B, auth checks).

</Steps>

## Caching headers

<CodeTabs id="cdn-headers" title="Headers for immutable assets, HTML pages, personalised APIs and revalidation" />

| Content | Strategy |
|---|---|
| JS/CSS/fonts/images from a build | Fingerprinted names + `max-age=31536000, immutable` |
| Product and article pages | Short `s-maxage` + `stale-while-revalidate`, purge by tag on change |
| Cacheable API responses (catalogue, config) | `s-maxage` of seconds to minutes; vary only on what matters |
| User-specific data | `private, no-store` — never in a shared cache |
| Video segments | Long TTL; manifests short TTL for live streams |

## Invalidation

- **Version URLs** wherever possible — new content, new name; nothing to purge, no stale risk.
- **Purge by tag / surrogate key**: tag responses (`product-42`) and purge all URLs with that tag in one API call; propagation takes seconds.
- **Avoid purge-everything** — the resulting cold cache sends a traffic spike to the origin.

## Private content

Paid videos, invoices and user uploads can still be served from the edge using **signed URLs** (or signed cookies for many files): the app signs the path and an expiry with a secret shared with the CDN; the edge verifies the signature and expiry without contacting the origin.

## Dynamic content and APIs

Even uncacheable requests benefit: the user's TLS handshake ends at a nearby PoP, and the CDN carries the request to the origin over warm, optimised long-haul connections. Edge compute can personalise cached pages (inserting a user's name into a cached shell) instead of skipping the cache entirely.

<Pitfalls>

- **Caching personalised responses** in a shared cache — users see each other's data.
- **Cookies or tracking parameters in the cache key** — near-zero hit rate.
- **Long TTLs on unversioned files** — users stuck on old JavaScript.
- **Purging everything** on each deploy.
- **No origin shield** — every PoP's miss hits the origin at once.
- **Forgetting `Vary`** when the response differs by `Accept-Encoding` or language.

</Pitfalls>

<KeyTakeaways>

- CDNs cut latency by distance and protect the origin by absorbing traffic.
- Cache-Control directs edges and browsers; fingerprint static assets and purge dynamic pages by tag.
- Shields and request coalescing keep origin load near one request per object.
- Signed URLs serve private content at the edge; never share-cache personalised responses.

</KeyTakeaways>
