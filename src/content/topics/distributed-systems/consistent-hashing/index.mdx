## Why it matters

Caches, databases and load balancers constantly answer "which server owns this key?". The naive `hash(key) % N` works until N changes — then almost every key moves, caches go cold all at once and databases are flooded. Consistent hashing limits movement to the keys the new or departed server actually owns. It's a core building block in [KV store](../../system-design/kv-store/), [distributed cache](../../system-design/distributed-cache/) and [sharding](../../databases/sharding/) designs.

<Callout type="analogy">
Seats around a round table. Guests (keys) sit and belong to the next host (server) clockwise. When a new host sits down, only the guests between the new host and the previous one change hosts — everyone else stays put. Giving each host several seats spread around the table (virtual nodes) keeps any one host from owning a huge empty stretch.
</Callout>

Replication: the next R **distinct** physical servers clockwise hold the replicas — skipping extra vnodes of a server already chosen.

## Other schemes

<CodeTabs id="hrw-jump" title="Rendezvous hashing and jump consistent hash" />

| Scheme | Lookup | Memory | Balance | Changes allowed | Used by |
|---|---|---|---|---|---|
| Ring + vnodes | O(log(N·V)) | N·V tokens | good with many vnodes | any server | Cassandra, Dynamo, many proxies |
| Rendezvous (HRW) | O(N) | none | very good | any server | CDNs, small clusters |
| Jump hash | O(log N) | none | near-perfect | only at the end (numbered buckets) | sharded storage with replicas per bucket |
| Fixed slots + map | O(1) | slot table | depends on assignment | move whole slots | Redis Cluster (16,384), Kafka partitions, virtual shards |
| Maglev | O(1) | lookup table | very good | any server, minimal disruption | Google's L4 load balancers |

The **fixed slots** approach is the one most systems use in practice: `slot = hash(key) % 16384` never changes; a small slot → node table is updated when rebalancing, and slots move one at a time while both nodes serve them.

## Hot keys and bounded loads

Hashing spreads *keys* evenly, not *traffic*. One celebrity key can overload its server regardless of scheme. Mitigations:

- **Consistent hashing with bounded loads**: cap each server at (1 + ε) × average load; if the chosen server is full, move to the next one clockwise (used in HAProxy and Vimeo's video serving).
- **Replicate <Term id="hot-partition">hot keys</Term>** to several servers and pick randomly among them; or add a local in-process cache in front ([Distributed cache](../../system-design/distributed-cache/)).
- **Split the key** (`counter:42#0..7`) and aggregate on read.

<Pitfalls>

- **`% N` for anything that grows** — mass reshuffles on every scaling event.
- **Too few virtual nodes** — some servers get several times their share.
- **Different hash functions or seeds on different clients** — keys land on different servers.
- **Counting vnodes as replicas** — two "replicas" on the same physical machine.
- **Ignoring hot keys** — even hashing doesn't mean even traffic.

</Pitfalls>

<KeyTakeaways>

- Consistent schemes move only ~1/N of keys when membership changes; modulo moves almost all.
- Ring + vnodes is the classic; rendezvous and jump hashing are simpler alternatives with trade-offs.
- Fixed hash slots with a slot map is the common production design.
- Balance keys with vnodes; balance traffic with bounded loads, replication and caching.

</KeyTakeaways>
