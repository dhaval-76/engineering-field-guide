## Why it matters

Thread pools, OOM kills, "too many open files", requests dropped on every deploy, a server whose CPU is busy but whose throughput won't grow: these are operating-system behaviours showing through your application. This group of pages builds the model behind them. This page covers processes, threads, scheduling and signals. [Memory](../memory-management/), [files and I/O](../files-and-io/) and [containers](../containers-in-os-terms/) follow.

<Callout type="analogy">
A shared kitchen. Each restaurant (process) has its own locked pantry (address space); cooks in the same restaurant (threads) share the pantry and must not grab the same pan at once. A few stoves (CPU cores) are shared by everyone, and the head chef (the scheduler) rotates cooks between them. Swapping one cook for another means putting away tools and setting up new ones: a context switch.
</Callout>

## Processes and threads

| | Process | Thread |
|---|---|---|
| Owns | Address space, open files, PID, environment | Its own stack, registers and thread-local storage |
| Shares | Nothing by default | Everything its process owns |
| Creating one | Heavier: new address space and kernel structures | Lighter: a new stack and a scheduler entry |
| A crash or memory bug | Stays inside that process | Can take down every thread in the process |
| Talking to others | Pipes, sockets, shared memory, files | Shared variables, with locks or atomics |

This is why **Chrome runs each tab (roughly, each site) in its own process**: a tab that crashes or gets compromised can't corrupt the others, at the cost of more memory. A Java service is usually one process with many threads, and isolation between services comes from separate processes and [containers](../containers-in-os-terms/).

Programs run in **user space** and ask the kernel for anything privileged, such as reading a file or opening a socket, through a **system call**. A system call costs far more than a function call, which is why buffered I/O batches them.

## Scheduling and context switches

The scheduler decides which runnable thread runs on each core and for how long. Threads that are waiting (for I/O, a lock or a sleep) don't compete. Linux used the Completely Fair Scheduler for years; Linux 6.6 replaced it with EEVDF, which also aims for fairness but handles latency-sensitive tasks better.

A **context switch** saves one thread's registers and loads another's. When the two threads belong to different processes, the address space changes too. The direct cost is microseconds; the indirect cost is that the new thread finds the CPU caches full of someone else's data.

**How many threads?** For CPU-bound work, about one per core: more threads only add switching. For work that mostly waits on I/O, more threads keep the cores busy: roughly cores × (1 + wait time ÷ compute time). The honest answer is to measure throughput and latency as you change the pool size. Java 21 virtual threads remove much of the question for blocking I/O, because a blocked virtual thread doesn't hold an OS thread. See [executors and thread pools](../../concurrency/executors-thread-pools/).

## Signals and graceful shutdown

A signal is a small asynchronous notification from the kernel or another process.

| Signal | Sent when | Can the process handle it? |
|---|---|---|
| SIGINT | Ctrl+C in a terminal | Yes |
| SIGTERM | "Please stop": `kill`, Kubernetes, systemd, Docker | Yes |
| SIGKILL | "Stop now": `kill -9`, the OOM killer, a timeout after SIGTERM | **No** |
| SIGHUP | Terminal closed; often reused to mean "reload config" | Yes |
| SIGCHLD | A child process exited | Yes |

On a deploy, Kubernetes sends SIGTERM, waits for the grace period (30 seconds by default), then sends SIGKILL. A service that ignores SIGTERM drops every in-flight request on every deploy. The right response: stop accepting new work, finish what's running, close connections, then exit.

A process killed by a signal exits with code **128 + the signal number**: 143 for SIGTERM (the JVM exits with 143 after its shutdown hooks run) and **137 for SIGKILL**, which in a container usually means the OOM killer. See [containers](../containers-in-os-terms/).

<Pitfalls>

- **Thousands of platform threads** for I/O-bound work: memory for stacks and time lost to switching. Use pools, async I/O or virtual threads.
- **CPU-bound pools far larger than the core count.**
- **Ignoring SIGTERM**, so every deploy drops requests.
- **A shell script as PID 1 in a container** that doesn't pass SIGTERM on to the application.
- **Child processes never waited for**, which pile up as zombies.

</Pitfalls>

<KeyTakeaways>

- Processes isolate; threads share memory and need synchronisation.
- fork copies (copy-on-write) and exec replaces; together they start programs.
- Context switches cost microseconds plus cold caches, so match thread counts to the work.
- Handle SIGTERM by draining; SIGKILL can't be handled, and exit code 137 means you were killed.

</KeyTakeaways>
