## Why it matters

A database promises your write is safe; a message broker serves gigabytes a second; a Node.js server holds 50,000 connections on one thread; another service dies with "too many open files". Each of these comes down to how the operating system does I/O: descriptors, the page cache, fsync, readiness notification and copying, or not copying, bytes.

<Callout type="analogy">
A restaurant. A **blocking** waiter stands at one table until the diners order. An **event-loop** waiter walks the floor and serves only tables that raise a hand (epoll). Writing down an order on a notepad is the page cache; it isn't safe until it is pinned on the kitchen board (fsync). **Zero-copy** is passing a dish straight from the kitchen to the table without the waiter replating it.
</Callout>

## File descriptors

Every open file, socket, pipe and epoll instance is a small integer, a **file descriptor**, indexing the process's table of open resources. A server holding 20,000 connections holds 20,000 descriptors.

- Each process has a limit (`ulimit -n`, often 1024 by default for interactive shells; services usually raise it). Hitting it gives `EMFILE`, "too many open files".
- When it happens, first look for a **leak**: sockets or files never closed, visible as a count that only grows in `/proc/PID/fd`, or many sockets stuck in CLOSE_WAIT. Then raise the limit to match the real need.
- Descriptors are inherited across fork and exec unless marked close-on-exec, which is how a shell connects a command's output to a file.

## The page cache and durability

Reads and writes normally go through the kernel's **page cache**, which keeps file data in RAM:

- A **read** of data already cached costs no disk access. That is why the second run of anything is faster, and why Linux's "free" memory is low on a healthy server: spare RAM is used as cache and given back on demand.
- A **write** copies data into the cache, marks it dirty and returns. The kernel writes it to disk later. If the machine loses power first, the write is gone, even though `write()` succeeded.
- **fsync** blocks until the file's data and metadata reach stable storage. Databases call it when they commit, which is what "durable" means.

## Blocking and non-blocking I/O

A blocking `read` on a socket parks the calling thread until data arrives. With one thread per connection, 10,000 mostly idle connections need 10,000 threads. The alternative is **non-blocking** sockets with **readiness notification**: ask the kernel which of thousands of sockets can be read or written right now, and only touch those.

<Walkthrough id="epoll-loop" />

- `select` and `poll` take the whole list of descriptors on every call, so they slow down as connections grow. **epoll** (Linux) and **kqueue** (BSD and macOS) register descriptors once and return only the ready ones.
- epoll is **level-triggered** by default: a socket with unread data is reported again on every wait. In **edge-triggered** mode it is reported once per change, so you must use non-blocking sockets and read until `EAGAIN`, or the rest of the data is stranded.
- **io_uring** works the other way round: you submit operations (read this, write that) to a ring shared with the kernel and collect completions from another, avoiding a system call per operation. It is fast but has had many security bugs; Docker's default seccomp profile blocks its system calls and Google restricted it on its servers.

| Model | How a server waits for 10,000 clients | Examples |
|---|---|---|
| Blocking, thread per connection | 10,000 OS threads, each blocked in `read` | Classic servlet containers, JDBC |
| Non-blocking + readiness (epoll, kqueue) | A few threads ask "which sockets are ready?" | Netty, Node.js, nginx, Redis |
| Completion-based (io_uring, IOCP) | Submit operations, collect completions | Newer runtimes and databases |
| Virtual or green threads | Blocking-style code; the runtime parks threads cheaply | Java 21 virtual threads, Go goroutines |

## Zero-copy

Sending a file over a socket the usual way copies every byte from the page cache into your program's buffer, then back into the kernel's socket buffer: two copies and two system calls per chunk. `sendfile` (Java `FileChannel.transferTo`, Python `os.sendfile`) asks the kernel to move the data from the page cache to the socket directly, never through user space.

This is a large part of why **Kafka** is fast: consumers read data that is usually still in the page cache, and the broker hands it to the socket with sendfile, without copying it through the JVM. Encryption breaks this, because TLS must read and transform every byte in user space, so Kafka over TLS loses zero-copy.

<Pitfalls>

- **Leaking descriptors** (unclosed sockets, files or HTTP responses) until `EMFILE`.
- **Treating `write()` returning as "saved"**, without fsync.
- **Renaming without fsyncing the file first**, or forgetting the directory fsync.
- **fsync on every small write** with no batching, capping throughput at the device's sync rate.
- **Blocking calls inside an event loop**, which stall every connection it serves.
- **Edge-triggered epoll without reading until `EAGAIN`.**

</Pitfalls>

<KeyTakeaways>

- Every file and socket is a descriptor, and descriptors are limited; leaks show up as EMFILE.
- Writes land in the page cache; fsync is what makes them durable, and it costs real time.
- Replace files with temp file, fsync, rename and directory fsync.
- epoll lets a few threads serve thousands of sockets; io_uring submits work and collects completions.
- sendfile moves file data to a socket without copying it through your program.

</KeyTakeaways>
