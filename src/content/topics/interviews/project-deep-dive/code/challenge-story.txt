SITUATION
"About 0.1% of card payments were charged twice — roughly 40 customers a day, each one
a support ticket and a refund."

WHY IT WAS HARD
"It didn't reproduce locally, and logs from the mobile app, gateway and payment service
couldn't be correlated."

WHAT I DID
"I added a correlation id to every hop and logged it. Within a day the pattern was clear:
mobile clients retried after a 10-second timeout, and our charge endpoint wasn't idempotent —
when the first response was lost, the retry charged again.
Options:
  1. Distributed lock on (customer, cart) in Redis — rejected: doesn't survive Redis failover,
     and a lock isn't a record of the result.
  2. Idempotency keys stored in Postgres with a unique constraint — chosen.
The client sends a key per payment attempt; the server records key + request hash +
outcome in the same transaction as the charge record; a repeat returns the stored outcome;
a concurrent duplicate gets 409 and retries."

RESULT
"Duplicate charges went from ~40/day to zero over the next three months; support tickets
for double charges disappeared. Correlation ids also cut our average debugging time."

REFLECTION
"I'd make idempotency a platform default for every mutating endpoint, not a fix per endpoint."

LIKELY FOLLOW-UPS — have answers ready
- What if the key store is down?            → fail closed for payments; return 503, client retries
- How long do you keep keys?                → 24 h, matched to the client's retry window
- Same key, different body?                 → 422: key reuse is a client bug
- What about the bank call itself?          → our own idempotency key passed to the provider
