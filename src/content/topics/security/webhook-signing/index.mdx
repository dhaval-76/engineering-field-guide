## Why it matters

A webhook endpoint is an unauthenticated public URL that triggers real actions: "payment succeeded, ship the order". Without verification, anyone who finds the URL can send a fake "payment succeeded". Without a timestamp check, an attacker who captured one genuine request can send it again later. Signature checks are a few lines of code, and getting them subtly wrong, with a non-constant-time comparison or a re-serialised body, is common.

<Callout type="analogy">
A wax seal plus a postmark. The seal (HMAC) can only be made with the sender's ring (the shared secret), so it proves who sent the letter and that it wasn't opened and changed. The postmark (timestamp) under the seal stops someone posting the same sealed letter again next week.
</Callout>

## How signing works

The sender and receiver share a secret. For each delivery the sender computes `HMAC-SHA256(secret, timestamp + "." + rawBody)` and sends it in a header with the timestamp. The receiver recomputes it from the same inputs and compares.

| | Stripe | GitHub |
|---|---|---|
| Header | `Stripe-Signature: t=1492774577,v1=5257a8…` | `X-Hub-Signature-256: sha256=7571…` |
| Signed content | timestamp, `.`, raw body | raw body |
| Algorithm | HMAC-SHA256, hex | HMAC-SHA256, hex |
| Replay protection | Timestamp, 5-minute default tolerance | None in the signature; use the delivery id |
| Rotation | Several `v1=` values during a secret roll | Change the secret in settings |

Including the timestamp **inside** the signed content matters: otherwise an attacker could replay an old body with a new timestamp.

## Getting the details right

<Walkthrough id="webhook-replay" />

- **Use the raw body.** Frameworks often parse JSON before your handler runs; re-serialising it can change spacing or key order and break the signature. Read the raw bytes for verification, then parse.
- **Constant-time comparison.** `==` stops at the first different character, and the time it takes can leak how much of a guess was right. Use `MessageDigest.isEqual`, `crypto.timingSafeEqual` or `hmac.compare_digest`.
- **Ignore unknown signature schemes** (such as Stripe's `v0` for tests), so an attacker can't downgrade to a weaker one.
- **Tolerance window**: about 5 minutes, and keep server clocks synchronised. A tolerance of 0, which some libraries treat as "don't check", disables replay protection.
- **Deduplicate by event id.** Providers deliver at least once, and a replay inside the window is still possible, so record processed ids and make handlers [idempotent](../../backend/idempotency/).
- **Respond quickly** (a 2xx), and do the work asynchronously, or the sender retries and you process duplicates.
- **Rotation**: during a secret change, the sender includes signatures with both secrets, or the receiver accepts either, until the old one is retired.

## Sending your own webhooks

Do the same in reverse: sign every delivery with a per-customer secret, include a timestamp and an event id, document the verification steps with a test vector, retry with backoff, and let customers rotate secrets. And treat the customer's URL as untrusted: delivering to it is an [SSRF](../ssrf/) risk. See [webhook delivery](../../system-design/webhook-delivery/) for the delivery system around it.

<Pitfalls>

- **No verification**, trusting the source IP or a secret in the URL.
- **Comparing signatures with `==`.**
- **Verifying a re-serialised body** instead of the raw bytes.
- **Signing the body without the timestamp**, or not checking the timestamp.
- **No deduplication by event id**, so retries and replays act twice.
- **Logging the signing secret** or committing it.

</Pitfalls>

<KeyTakeaways>

- Verify every webhook with an HMAC over the timestamp and raw body.
- Compare in constant time and reject anything outside a short tolerance.
- Deduplicate by event id and keep handlers idempotent.
- Rotate secrets with an overlap, and when you send webhooks, sign them the same way.

</KeyTakeaways>
