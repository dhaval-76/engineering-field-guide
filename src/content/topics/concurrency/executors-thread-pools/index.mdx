## Why it matters

Creating a platform thread is expensive (an OS thread and about a megabyte of stack), and unbounded concurrency is how services fall over: every slow request ties up a thread, threads pile up, memory runs out. A thread pool reuses a fixed set of threads and — configured properly — gives you **<Term id="backpressure">backpressure</Term>**: when you're overloaded you reject or slow down instead of collapsing. Most production incidents involving executors come from the defaults.

<Callout type="analogy">
A restaurant kitchen with a set number of cooks and an order rail. Orders wait on the rail when the cooks are busy; when the rail is full the manager calls in extra cooks; when even they're busy, the host stops seating people. A kitchen that hires a new cook for every order — or lets the rail grow down the street — isn't a working kitchen.
</Callout>

The counter-intuitive part: extra threads above core are created **only when the queue is full**. With an unbounded queue (`newFixedThreadPool`), the pool never grows beyond core and the queue grows until memory runs out.

| Factory | Hidden configuration | Risk |
|---|---|---|
| `newFixedThreadPool(n)` | n threads, **unbounded** `LinkedBlockingQueue` | Memory exhaustion and huge latency under overload |
| `newCachedThreadPool()` | 0 core, **unbounded** max, no queue | Thousands of threads, OOM |
| `newSingleThreadExecutor()` | 1 thread, unbounded queue | Same as fixed |
| `newVirtualThreadPerTaskExecutor()` | One virtual thread per task | Fine for I/O; protect downstreams with semaphores |

- **CPU-bound** work: about one thread per core; more just adds context switching.
- **I/O-bound** work: threads mostly wait, so more threads keep the CPU busy — the formula above, or **<Term id="little-law">Little's law</Term>** (`concurrency = throughput × latency`).
- **Downstream limits** usually matter more: a pool of 200 threads hitting a database pool of 20 connections just queues 180 threads inside the <Term id="connection-pool">connection pool</Term>.
- **Waiting work needs either many threads or cheap ones.** Measured: 10,000 tasks that each block for 100 ms (a stand-in for a database or HTTP call), JDK 22 on 8 cores:

<Chart

  log
  unit=" s"
  caption="Log scale. The work is all waiting, so time ≈ tasks × 100 ms ÷ threads. A pool sized for CPU work (8) is useless here; virtual threads make one thread per task affordable."
/>

- Use **separate pools** (bulkheads) for different kinds of work, so slow reports can't starve checkout.
- Then **measure**: queue depth, active threads, rejections and latency under load.

<Pitfalls>

- **Unbounded queues and thread counts** from the `Executors` factories.
- **Blocking I/O on the common ForkJoinPool** (parallel streams, default `CompletableFuture.supplyAsync`).
- **Tasks that wait for other tasks in the same bounded pool** — thread-starvation <Term id="deadlock">deadlock</Term>.
- **Never shutting down** custom pools — non-daemon threads keep the JVM alive; leaked pools in redeploys.
- **Silent failures** with `execute` and no uncaught-exception handling.

</Pitfalls>

<KeyTakeaways>

- Core → queue → max → reject: bound the queue so max and rejection actually happen.
- Size by CPU vs I/O, then by downstream limits; measure under load.
- `submit` with timeouts to see failures; shut down gracefully.
- Virtual threads for high-concurrency I/O; bounded platform pools for CPU work.

</KeyTakeaways>
