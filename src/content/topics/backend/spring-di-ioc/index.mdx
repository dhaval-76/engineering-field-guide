## Why it matters

In a service of any size, objects depend on other objects: controllers on services, services on repositories and clients, clients on configuration. If every class constructs its own collaborators with `new`, the dependencies are hard-wired — you can't swap Stripe for a fake in tests or configure a timeout per environment. **Inversion of control** hands construction and wiring to a container, so classes only declare what they need. Spring's container is the backbone of every Spring Boot application, and its behaviour explains most confusing startup errors and many production bugs (shared state in singletons, transactions that silently don't apply).

<Callout type="analogy">
A restaurant kitchen. A chef doesn't grow vegetables or forge knives; they list what they need, and the restaurant supplies it. Change supplier and the recipe still works. Dependency injection is the chef listing ingredients in the recipe (the constructor) instead of fetching them from a specific farm.
</Callout>

## Scopes

<CodeTabs id="bean-scopes" title="Singleton, prototype and request scope" />

| Scope | Instances | Watch out for |
|---|---|---|
| `singleton` (default) | One per container | Shared by all threads — no mutable request state in fields |
| `prototype` | New per request to the container | Injected once into a singleton = one instance forever; Spring doesn't destroy prototypes |
| `request` / `session` | One per HTTP request / session | Needs a scoped proxy when injected into singletons |
| `application` | One per `ServletContext` | Rarely needed |

## Configuration

<CodeTabs id="config-properties" title="Typed, validated configuration" />

<CodeTabs id="auto-configuration" title="How auto-configuration decides what to create" />

Starters bring libraries plus auto-configurations; each applies only when its conditions hold (`@ConditionalOnClass`, `@ConditionalOnProperty`, `@ConditionalOnMissingBean`), so defining your own bean replaces the default.

<Pitfalls>

- **Mutable fields in singleton beans** (e.g. storing the current user) — a concurrency bug across requests.
- **Field injection** hiding ten dependencies — a class doing too much.
- **Prototype injected directly into a singleton**, expecting fresh instances.
- **Calling `@Transactional` / `@Async` methods from `@PostConstruct`** or from the same class — no proxy, no behaviour (see [AOP](../spring-aop/)).
- **`@Value` strings scattered everywhere** instead of typed properties.
- **Enabling circular references** to make startup pass.

</Pitfalls>

<KeyTakeaways>

- The container builds and wires beans; constructor injection keeps classes honest and testable.
- `@Component` for your classes, `@Bean` for others' or special construction.
- Singletons are shared: keep them stateless.
- Lifecycle: instantiate → inject → init → proxy → use → destroy.
- Cycles mean a design problem; typed config and conditional auto-configuration keep setup explicit.

</KeyTakeaways>
