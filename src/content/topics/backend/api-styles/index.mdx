## Why it matters

Every service boundary needs a contract. The protocol you pick decides how easy the API is to consume, cache, evolve, debug and secure, and how much data crosses the network. Most real systems use several styles — the skill is matching each boundary to the right one, and explaining why.

<Callout type="analogy">
A restaurant. **<Term id="rest">REST</Term>** is a set menu by dish: fixed plates at known addresses. **GraphQL** is a buffet where you fill one plate with exactly what you want, in one trip. **gRPC** is the kitchen's internal ticket system — terse, fast, and only the staff understand it. **Async** is "we'll text you when your table is ready".
</Callout>

## At a glance

| Aspect | REST | GraphQL | gRPC | Async (events/webhooks) |
|---|---|---|---|---|
| Contract | OpenAPI (optional) | Schema (required) | `.proto` (required) | Event schema (Avro/JSON Schema/Protobuf) |
| Transport / format | HTTP/1.1–3, JSON | HTTP POST, JSON | HTTP/2, binary Protobuf | Broker (Kafka, queues) or HTTP callbacks |
| Who shapes the response | Server | Client | Server | Producer |
| HTTP caching | Natural (GET + ETag/CDN) | Hard (POST); persisted queries help | None | n/a |
| Streaming | SSE, chunked | Subscriptions (usually WebSocket) | Built in (client, server, bidirectional) | Inherent |
| Browser support | Native | Native | Needs grpc-web or a gateway | Webhooks are server-to-server |
| Best for | Public/partner APIs, simple CRUD | Many client types needing different shapes | Internal low-latency calls, polyglot services | Decoupling, fan-out, slow work |

## REST

Covered in depth in [REST API design](../rest-api-design/). Its strengths are the web's: URLs, verbs, status codes, caching, and tooling everyone already has. Weaknesses: over-fetching (big fixed responses), under-fetching (several round trips to assemble a screen), and no enforced schema unless you adopt OpenAPI.

## GraphQL

A typed schema describes the graph; clients send queries selecting exactly the fields they need; each field has a **resolver**.

Production concerns:

- **<Term id="n-plus-one">N+1</Term>** — batch every relation (DataLoader, `@BatchMapping`).
- **Abuse** — a single query can request a huge nested graph. Limit depth and complexity, paginate every list, and use **persisted queries** (an allow-list of query hashes) for first-party apps.
- **Caching** — responses vary per query; cache inside (DataLoader per request, entity caches) or use persisted queries over GET for <Term id="cdn">CDN</Term> caching.
- **Errors** — HTTP 200 with an `errors` array; expected business errors are better modelled in the payload (`CancelOrderPayload.errors`).
- **Authorization** — per field/object in the service layer, not by hiding schema fields.

## gRPC

Define services and messages in Protobuf; code generators produce typed clients and servers in every major language. Messages are compact binary over <Term id="http2">HTTP/2</Term> multiplexed connections.

Production concerns:

- **Deadlines** on every call, propagated downstream — gRPC carries the remaining deadline across hops.
- **Status codes** (`NOT_FOUND`, `UNAVAILABLE`, `DEADLINE_EXCEEDED`, …) replace HTTP statuses; retry only <Term id="idempotency">idempotent</Term> calls on `UNAVAILABLE`.
- **Load balancing** — HTTP/2 keeps one long-lived connection, so an L4 <Term id="load-balancer">load balancer</Term> pins a client to one pod. Use client-side balancing (`round_robin` over <Term id="dns">DNS</Term>), an L7 proxy (Envoy) or a service mesh.
- **Browsers** need grpc-web or a REST/JSON gateway (gRPC-Gateway, Envoy transcoding).
- **Compatibility** — add fields with new numbers; never change a field's type or reuse a number (`reserved`); unknown fields are ignored by old clients.

## Asynchronous APIs

When the caller doesn't need the result now, or several services react to the same fact, publish an **event** ("OrderPlaced") to a <Term id="message-broker">broker</Term> ([Kafka vs RabbitMQ](../../distributed-systems/kafka-vs-rabbitmq/)). For external consumers, **webhooks** push events over HTTP — signed, retried with backoff, idempotent on the receiver ([Webhook delivery](../../system-design/webhook-delivery/)). Async APIs need schemas and versioning too (a schema registry), and consumers must tolerate duplicates and reordering.

## Choosing

<Steps>

1. **Public or partner API?** REST with OpenAPI (plus webhooks for events). Universally consumable, cacheable, documented.
2. **Several frontends with different data needs?** GraphQL, usually in a backend-for-frontend that calls internal services.
3. **Service-to-service, latency-sensitive, many languages?** gRPC.
4. **Caller shouldn't wait, or many consumers?** Events through a broker.
5. **Small team, one TypeScript app?** tRPC or plain REST — don't adopt GraphQL or gRPC infrastructure you don't need.

</Steps>

<Pitfalls>

- **GraphQL without batching or query limits** — N+1 floods and denial-of-service by query.
- **gRPC behind an L4 load balancer** — all traffic from a client lands on one pod.
- **No deadlines** — a slow dependency holds threads across the call chain.
- **Reusing Protobuf field numbers** or renaming enum values — silent data corruption between versions.
- **Exposing internal gRPC or event schemas directly to partners** — couples them to your internals.
- **Choosing by fashion** — the protocol should follow the consumer.

</Pitfalls>

<KeyTakeaways>

- REST for public APIs, GraphQL for flexible client queries, gRPC for internal calls, events for decoupling.
- GraphQL needs batching, query cost limits and field-level authorization.
- gRPC needs deadlines, L7/client-side load balancing and careful Protobuf evolution.
- Most systems mix styles at different boundaries.

</KeyTakeaways>
