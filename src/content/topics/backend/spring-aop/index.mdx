## Why it matters

Some concerns cut across every layer: start a transaction, check permissions, time the call, cache the result, retry on failure. Writing them inside each method buries business logic and invites copy-paste mistakes. **Aspect-oriented programming** declares them once and applies them to many methods. Spring uses it for its own core features — `@Transactional`, `@Async`, `@Cacheable`, `@PreAuthorize`, `@Retryable` are all proxies — so understanding proxies explains a classic production bug: an annotation that silently does nothing.

<Callout type="analogy">
A receptionist in front of an office. Visitors talk to the receptionist, who signs them in, checks their badge and notes the time before showing them through — the person they're visiting doesn't do any of that. But a colleague walking over from the next desk never passes reception: no sign-in, no badge check. That's a self-call.
</Callout>

## How the proxy works

| Term | Meaning |
|---|---|
| **Aspect** | A class holding cross-cutting logic (`@Aspect`) |
| **Join point** | A point where advice can run — in Spring AOP, a method execution |
| **Pointcut** | An expression selecting join points (`execution(...)`, `@annotation(...)`, `within(...)`) |
| **Advice** | The code to run: `@Before`, `@AfterReturning`, `@AfterThrowing`, `@After`, `@Around` |
| **Weaving** | Applying aspects — Spring does it at runtime with proxies (JDK dynamic proxies for interfaces, CGLIB subclasses by default in Boot); AspectJ can weave at compile or load time |

## When advice silently doesn't apply

<CodeTabs id="aop-self-invocation" title="Self-invocation and its fixes" />

Other `@Transactional` details that cause surprises:

- **Rollback rules**: by default only unchecked exceptions (`RuntimeException`, `Error`) roll back; checked exceptions commit unless you set `rollbackFor`.
- **Catching the exception inside the transaction** and continuing — the transaction may already be marked rollback-only, giving `UnexpectedRollbackException` at commit.
- **Propagation**: `REQUIRED` (default) joins an existing transaction; `REQUIRES_NEW` suspends it and starts another (use for audit logs that must survive a rollback) — it needs a second connection.
- **`readOnly = true`** lets Hibernate skip dirty checking and lets drivers route to replicas; it doesn't stop writes by itself on every database.
- **Exceptions thrown from `@Async` methods** don't reach the caller; return a `CompletableFuture` or configure an `AsyncUncaughtExceptionHandler`.

## Events for decoupled side effects

<CodeTabs id="aop-events" title="Publish an event, react after commit" />

<Pitfalls>

- **Self-invocation**, private or final methods — the annotation does nothing, without an error.
- **Swallowing exceptions in `@Around`** — callers think the call succeeded.
- **Overly broad pointcuts** (`execution(* *(..))`) advising framework beans and slowing everything.
- **Expecting checked exceptions to roll back**.
- **Long `@Transactional` methods** with remote calls inside (see [connection pooling](../connection-pooling/)).
- **Implementing authentication with a homemade aspect** instead of Spring Security's filters and method security.

</Pitfalls>

<KeyTakeaways>

- Spring AOP = runtime proxies around beans; advice runs only for calls through the proxy.
- `@Transactional`, `@Async`, `@Cacheable`, `@PreAuthorize` follow the same rules.
- Move advised methods to another bean or make them the entry point; mind rollback rules and propagation.
- Events + after-commit listeners decouple side effects; outbox for guaranteed delivery.

</KeyTakeaways>
