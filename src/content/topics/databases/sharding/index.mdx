## Why it matters

Replication scales reads, but every write still goes through one primary, and every replica stores everything. When writes or data size outgrow one machine, you split the data so each machine owns a part. Sharding gives near-linear capacity — and takes away things a single database gives for free: joins and transactions across all data, globally unique sequences, simple backups and schema changes. It's the most consequential and least reversible scaling step, so it's worth knowing both how and when not to.

<Callout type="analogy">
A library that outgrows its building opens branches. Splitting by the first letter of the author's surname (range) keeps shelves browsable but the "S" branch is overloaded. Splitting by a hash of the ISBN spreads books evenly, but "all books by Smith" now means visiting every branch. Whatever rule you pick, readers should usually find what they need in one branch.
</Callout>

## Before you shard

| Step | Buys you |
|---|---|
| Fix queries and indexes | often 10–100× |
| Bigger instance (vertical scaling) | modern servers have 100+ cores and TBs of RAM |
| Read replicas + caching | read scaling |
| Archive or delete old data; table partitioning | smaller working set, cheap retention |
| Split by feature (separate databases per service) | each database carries less |
| Shard | write and storage scaling, at a large complexity cost |

## Partitioning inside one database

PostgreSQL and MySQL can split one logical table into partitions by range, list or hash. Queries that filter on the partition key touch only matching partitions (**partition pruning**), and dropping a month of old data is an instant `DROP` of a partition instead of a huge `DELETE`.

## Sharding strategies

<Walkthrough id="shard-routing" />

| Strategy | How a key finds its shard | Strengths | Weaknesses |
|---|---|---|---|
| **Range** | key ranges: `A–F`, `G–M`… or by date | range scans and ordered pagination stay on one shard | hot spots (all new rows land on the newest range); manual splits |
| **Hash** | `hash(key)` → shard | even distribution | range queries hit every shard; naive modulo makes resharding painful |
| **Directory** (lookup) | a table maps key → shard | move individual tenants/users; mix shard sizes | the directory is a dependency to cache and keep available |
| **Geographic** | user's region → shard in that region | latency, data residency rules | uneven regions; users who move |

Fixed **virtual shards** (say 1,024 logical buckets, `hash(key) % 1024`, with a small map from bucket to physical database) are the most common practical answer: adding a machine means moving some buckets, not rehashing keys. Consistent hashing (a hash ring) does the same job and is covered in system design.

## Choosing a shard key

<CodeTabs id="shard-router" title="Routing by tenant through virtual shards" />

A good shard key:

- **appears in almost every query** — otherwise queries must ask all shards;
- **spreads load evenly** — many distinct values, no single value dominating;
- **keeps related data together** — a customer with their orders and invoices, so their transactions stay on one shard;
- **doesn't change** — moving a row between shards is a migration.

| Product | Common shard key | Why |
|---|---|---|
| B2B SaaS | `tenant_id` | every query is within a tenant; huge tenants may need their own shard |
| Consumer app | `user_id` | a user's data together; feeds/messages fan out |
| Chat | `conversation_id` | messages read per conversation |
| Orders at scale | `customer_id` (not `order_id`) | "my orders" is one shard; lookups by order id carry the customer id or use an index table |

**Hot keys** remain the classic failure: a celebrity's followers, a giant tenant, one viral product. Options: split that key further (`key#0…key#7` with a suffix and merge on read), give it a dedicated shard (directory), or cache it.

## Living with shards

- **Cross-shard queries** become scatter-gather: send to all shards, merge, sort, paginate — latency of the slowest shard. Keep a separate read model (search index, warehouse) for global queries.
- **Cross-shard transactions** need two-phase commit or a saga; design aggregates so a business transaction touches one shard.
- **Unique ids** can't come from one sequence: use UUID v7, Snowflake-style ids (time + machine + sequence), or per-shard ranges.
- **Uniqueness across shards** ("username is unique") needs a separate global table or service.
- **Schema changes** run on every shard; automate them.
- **Resharding** online: copy data to the new layout (snapshot + change stream), dual-read/verify, switch routing per bucket, clean up — tools like Vitess (MySQL) and Citus (PostgreSQL) automate much of this, and distributed SQL databases (CockroachDB, Spanner, YugabyteDB) shard and rebalance automatically.

<Pitfalls>

- **Sharding too early** — losing joins, transactions and simplicity for scale you don't need.
- **A shard key missing from most queries** — every request becomes scatter-gather.
- **Monotonic keys with range sharding** (timestamps, auto-increment ids) — all writes hit the last shard.
- **`hash % N` routing** — adding a shard reshuffles almost everything.
- **Ignoring the biggest tenant/user** — one key bigger than a shard.
- **Auto-increment ids per shard** — collisions when data is merged or moved.

</Pitfalls>

<KeyTakeaways>

- Partition tables for maintenance and pruning; shard only when one primary can't keep up.
- The shard key must be in the queries, spread load, and group related data.
- Use virtual shards or consistent hashing so growth moves few keys.
- Plan for hot keys, scatter-gather reads, global ids and uniqueness, and online resharding.

</KeyTakeaways>
