## Recognise it

- A sort-then-scan feels natural: intervals by end, tasks by deadline, items by ratio.
- You can track a single summary of the past ("farthest reachable index", "current fuel") instead of all options.
- Choosing the extreme option (earliest, largest, most frequent) leaves the most freedom for the rest.

<Callout type="analogy">
Packing for a flight with a weight limit when every item is equally useful: take the lightest items first and you fit the most. That simple rule is provably best here — but if items had different values, "lightest first" could leave the most valuable thing behind, and you'd need to compare combinations (dynamic programming).
</Callout>

### Task scheduler with cooldown

Identical tasks must be at least n slots apart. The most frequent task dictates the frame: `(maxCount − 1)` gaps of size `n + 1`, plus the tasks tied for the maximum in the final slot. If there are enough other tasks to fill every gap, no idling is needed and the answer is simply the number of tasks.

## When greedy fails

| Problem | Tempting greedy | Why it fails | Use |
|---|---|---|---|
| Coin change (arbitrary coins) | largest coin first | {1, 3, 4}, amount 6 → 3 coins vs optimal 2 | DP |
| 0/1 knapsack | best value/weight first | can't take fractions; ratios mislead | DP |
| Longest path | always take the longest next edge | local choices block better routes | DP on DAGs / search |
| Fractional knapsack | best value/weight first | — works, items are divisible | greedy ✓ |

<Pitfalls>

- **Assuming greedy works** without an argument or a counter-example search.
- **Sorting by the wrong key** (start instead of end for interval scheduling).
- **Ignoring ties** that affect correctness.
- **Overflow** in running sums.

</Pitfalls>

<KeyTakeaways>

- Greedy commits to local choices; prove them with exchange arguments.
- Track compact state: farthest reach, running balance, last occurrence.
- Test small counter-examples; fall back to DP when choices interact.

</KeyTakeaways>
