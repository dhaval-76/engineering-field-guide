## Why it matters

Many problems need the **current best item** over and over while new items keep arriving: the next task to run, the closest unvisited city, the cheapest order in a book, the K most frequent search terms. Sorting after every insertion costs O(n log n) each time. A **heap** keeps the minimum (or maximum) at the top with **O(log n)** inserts and removals and O(1) access to the top — the right tool whenever "give me the best, then let me add more" repeats.

Heaps run inside OS schedulers, timer wheels and delayed-job queues, <Term id="dijkstra">Dijkstra</Term>'s shortest paths ([Shortest paths](../shortest-paths/)), the merge step of databases' external sort, and every "top K" dashboard. Java's `PriorityQueue` and Python's `heapq` are binary heaps.

<Callout type="analogy">
A hospital emergency room: patients don't leave in arrival order but by urgency. The triage desk always knows who is most urgent, and a new arrival doesn't force re-sorting everyone — they are slotted in with a few comparisons against the people "above" them.
</Callout>

## Recognise it

- "**K** largest / smallest / most frequent / closest" → a size-K heap (or quickselect).
- Repeatedly take the **next earliest / cheapest** item while adding new ones → a priority queue (scheduling, simulations, Dijkstra).
- **Merge sorted** streams or lists → a heap of the current head of each.
- **Median or percentile of a stream** → two heaps.
- "How many resources are busy at once?" (rooms, servers, CPUs) → a heap of end times.

## How a binary heap works

<Walkthrough id="heap-ops" />

A binary heap is a **complete binary tree stored in an array** — no pointers. For index `i`, the children are `2i + 1` and `2i + 2`, and the parent is `(i − 1) / 2`. The **heap property** — every parent ≤ its children (min-heap) — guarantees the minimum is at index 0. It does *not* sort the rest: siblings can be in any order.

- **Push**: append at the end, then **sift up** — swap with the parent while smaller. At most one path from leaf to root: O(log n).
- **Pop**: take the root, move the last element to the root, then **sift down** — swap with the smaller child while larger. O(log n).
- **Peek**: index 0, O(1).
- **Heapify** n elements: sift down every internal node from the bottom up — **O(n)**, not O(n log n), because most nodes are near the leaves and move only a step or two.

## Worked problems

### Kth largest element / top-K

**Insight.** Keep a **min-heap of the K largest values seen so far**. Its root is the smallest of them — the Kth largest. Each new value larger than the root replaces it; smaller values are ignored after one comparison. O(n log K) time and only O(K) memory, so it works on a stream that doesn't fit in memory.

<CodeTabs id="dsa-top-k" title="Kth largest and top-K frequent — size-K heaps" />

### Quickselect

**Insight.** When all the data is in an array and you only need the Kth value, partition around a pivot as quicksort does: after one partition the pivot sits at its final sorted position. If that position is the target, done; otherwise continue in **one** side only. Expected work is n + n/2 + n/4 + … ≈ 2n: **O(n) on average**. A random pivot makes the O(n²) worst case vanishingly unlikely. It rearranges the array and doesn't return the top K in order.

### Merge K sorted lists

**Insight.** The next smallest element overall is the smallest of the K current heads. Keep those heads in a min-heap: pop the smallest, append it to the result, and push its successor. O(N log K) for N total elements — the same algorithm merges sorted runs in an external sort and merges SSTables in LSM databases.

### Meeting rooms II

**Problem.** The minimum number of rooms so that overlapping meetings never share one. `[[0,30],[5,10],[15,20]]` → 2.

**Insight.** Process meetings by start time and keep a min-heap of **end times of rooms in use**. If the earliest-ending room is free by the time the next meeting starts, reuse it (pop); then push the new meeting's end. The heap's size is the number of rooms in use at once. (Without a heap, sorting the starts and the ends separately and sweeping gives the same count — the second function below. More interval techniques are in [Intervals](../intervals/).)

### Find the median of a data stream

**Insight.** Split the numbers into a lower half in a **max-heap** and an upper half in a **min-heap**, keeping sizes within one of each other. Every value in the lower half is ≤ every value in the upper half, so the median is the top of the larger heap, or the average of both tops. Each insert is O(log n); reading the median is O(1).

## Choosing an approach for top-K

| Approach | Time | Space | Use when |
|---|---|---|---|
| Sort everything | O(n log n) | O(n) | you need everything sorted anyway |
| Size-K heap | O(n log K) | O(K) | streams, K ≪ n, data doesn't fit in memory |
| Quickselect | O(n) average | O(1) | all data in an array, order of the K not needed |
| Bucket counting | O(n) | O(n) | top-K **frequent**, counts bounded by n ([Hashing](../arrays-and-hashing/)) |

## Heap or balanced tree?

A `TreeMap`/sorted set also gives the minimum in O(log n), and it can find, delete or update **any** element in O(log n) and iterate in order. A heap only gives fast access to the top, and removing an arbitrary element is O(n) in Java's `PriorityQueue`. In return the heap is an array — less memory, better cache behaviour, O(n) construction. Use a heap when you only ever need the top; use a tree when you need to update or remove arbitrary entries (or use a heap with **lazy deletion**: mark entries stale and skip them when they reach the top).

## Talking through it in an interview

- Say which heap you use and why: "a **min**-heap of size K for the K **largest**, because I want to evict the smallest of them quickly".
- Give the complexity in terms of both n and K.
- Mention quickselect as the O(n) average alternative, and its trade-offs (mutates the input, unordered result, bad worst case).
- Know your language: Java's `PriorityQueue` and Python's `heapq` are min-heaps; JavaScript has none built in.

<Pitfalls>

- **A max-heap of everything for top-K largest** — O(n log n) and O(n) memory; a size-K min-heap is cheaper.
- **Comparators that overflow** (`a - b` with large ints) — use `Integer.compare`.
- **Python max-heaps** — push negated values (or tuples with negated keys).
- **Ties with uncomparable payloads** in Python tuples — add a counter as a tiebreaker.
- **Iterating a `PriorityQueue` and expecting sorted order** — only repeated `poll` returns elements in order.
- **Removing arbitrary elements** from a `PriorityQueue` in a loop — O(n) each; use lazy deletion or a tree.

</Pitfalls>

<KeyTakeaways>

- A heap keeps the best element on top with O(log n) updates; building one is O(n).
- Size-K min-heap for the K largest; heap of heads for K-way merges; two heaps for medians; heap of end times for resource counting.
- Quickselect finds the Kth value in O(n) average when the data is all in memory.

</KeyTakeaways>
