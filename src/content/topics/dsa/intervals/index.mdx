## Why it matters

Intervals are everywhere in backend systems: meeting and room bookings, hotel and seat reservations ([Ticket booking](../../system-design/ticket-booking/)), on-call schedules, time windows in rate limiters, IP and date ranges, TTLs, and video segments. The same handful of questions keeps coming up — *do these overlap? merge them; how many happen at once? what's free?* — and a naive pairwise comparison is O(n²).

Almost every interval problem becomes O(n log n) — or O(n) if already sorted — once you **sort** by the right endpoint and sweep once. Choosing *which* endpoint to sort by is the whole trick.

<Callout type="analogy">
A shared calendar. To merge busy blocks, read them in order of start time and extend the current block while the next one starts before it ends. To count how many rooms you need, walk through the day noting how many meetings are running at each moment — the peak is the answer. To fit in as many meetings as possible, always pick the one that finishes earliest.
</Callout>

## Recognise it

<Callout type="spot">

**Wording clues**

- A list of `[start, end]` pairs: meetings, reservations, ranges, time windows.
- Merge overlaps, insert a new range, minimum removals to avoid overlap, how many resources at once, free gaps, intersections of two schedules, accept or reject a booking as it arrives.

**Constraint clues**

- n up to 10⁵ intervals → sort once, O(n log n), then a single sweep; comparing every pair (O(n²)) is too slow.
- Bookings arrive **one at a time** and must be answered immediately → a sorted map (TreeMap) of starts.
- Coordinates up to 10⁹ → sort the endpoints; don't allocate an array over the whole range.

**Looks like it, but isn't**

- **Points** rather than ranges, or one sorted array → [binary search](../binary-search/) or [two pointers](../two-pointers/).
- Ranges with **weights** and "maximise total value" of non-overlapping ones → dynamic programming plus binary search, not greedy.

</Callout>

## Overlap, precisely

Two intervals `[a, b]` and `[c, d]` overlap exactly when **`a < d` and `c < b`** (each starts before the other ends). Everything else is a variation of this test. Decide the endpoint convention first:

- **Closed** `[1, 2]` and `[2, 3]` share the point 2 → they overlap (typical for "merge intervals").
- **Half-open** `[1, 2)` and `[2, 3)` don't → a room freed at 2 can be reused at 2 (typical for meetings and bookings).

## Worked problems

### Merge intervals

<Clues>"**merge** overlapping ranges" → sort by start, extend the current block.</Clues>

**Insight.** After sorting by start, an interval can only overlap the **current merged block** (everything earlier ends before the block starts). So keep one current block: if the next interval starts at or before its end, extend the end to the larger of the two; otherwise close the block and start a new one.

### Insert an interval

<Clues>already **sorted and disjoint** + one new range → three passes (before, overlapping, after) in O(n), no sort.</Clues>

**Insight.** The list is already sorted and disjoint, so no sort is needed: copy every interval that ends before the new one starts; merge every interval that overlaps it into one (min of starts, max of ends); copy the rest. Three phases, O(n).

<CodeTabs id="dsa-insert-interval" title="Insert an interval into a sorted, non-overlapping list — O(n)" />

### Keep the most non-overlapping intervals

**Problem.** Remove the fewest intervals so that the rest don't overlap.

<Clues>"**fewest removals** so the rest don't overlap" → greedy: sort by **end**, keep each interval that starts after the last kept end.</Clues>

**Insight.** Equivalent to keeping the most. Sort by **end** and greedily keep each interval that starts at or after the last kept one ends. Why it's safe: among all intervals that could come first, the one that **finishes earliest** leaves the most room for the others — swapping it into any optimal solution never makes that solution worse (an *exchange argument*, see [Greedy](../greedy/)). Sorting by start fails: one long early interval would block many short ones.

<CodeTabs id="dsa-non-overlapping" title="Non-overlapping intervals — earliest end first" />

### How many rooms?

<Clues>"how many **at once**?" → sort by start with a min-heap of end times, or sweep start and end events.</Clues>

**Insight.** The number of rooms equals the **maximum number of meetings running at the same moment**. Sort by start and keep a <Term id="heap">min-heap</Term> of end times of rooms in use (reuse the earliest-ending room when it's free), or turn every meeting into two events, +1 at its start and −1 at its end, and sweep them in time order — processing ends before starts at equal times for half-open intervals.

<CodeTabs id="dsa-meeting-rooms" title="Minimum meeting rooms — min-heap of end times, and sweep line" />

### Intersections of two schedules

**Problem.** Two people's free times, each a sorted list of disjoint intervals. When are both free?

<Clues>two **sorted, disjoint** lists → two pointers, advancing whichever interval ends first.</Clues>

**Insight.** Two pointers. The intersection of the current pair is `[max of starts, min of ends]`, if non-empty. Then advance the interval that **ends first** — it can't intersect anything further in the other list, while the longer one might.

<CodeTabs id="dsa-interval-intersections" title="Interval list intersections — two pointers" />

### A calendar that rejects double bookings

**Problem.** Bookings `[start, end)` arrive one at a time; accept each only if it overlaps no accepted booking.

<Clues>bookings arrive **one at a time** and need an immediate answer → a sorted map; check only the neighbours of the new start.</Clues>

**Insight.** Checking every booking is O(n) per request. Keep bookings in a **sorted map keyed by start**. Only two existing bookings can clash: the one starting just before the new start (does it end after the new start?) and the one starting at or just after (does it start before the new end?). With a balanced tree (`TreeMap`) both lookups and the insert are O(log n). This is the core of a room- or seat-booking service ([Meeting room LLD](../../low-level-design/meeting-room/)); with concurrent requests, the check and the insert must happen atomically (a lock, or a database constraint).

## Complexity at a glance

| Problem | Sort by | Technique | Time |
|---|---|---|---|
| Merge intervals | start | extend current end | O(n log n) |
| Insert interval | (already sorted) | three phases | O(n) |
| Max non-overlapping / min removals | end | greedy earliest finish | O(n log n) |
| Min rooms / max overlap | start, or event time | heap of ends / ±1 sweep | O(n log n) |
| Intersections of two lists | (both sorted) | two pointers | O(m + n) |
| Online booking | start (sorted map) | check neighbours | O(log n) per booking |

## Talking through it in an interview

- Ask about the endpoint convention: do touching intervals overlap?
- Say which endpoint you sort by and why (start for merging, end for selection).
- For <Term id="greedy">greedy</Term> selection, give the one-line exchange argument.
- For online versions, mention the sorted map and concurrency (two requests booking the same slot).

<Pitfalls>

- **Sorting by end when merging** (or by start for max non-overlapping) — the argument breaks.
- **Touching endpoints** treated inconsistently — decide closed vs half-open first.
- **Only comparing with the previous interval** when merging, instead of the current merged block's end.
- **Mutating input intervals** that the caller still uses.
- **Sweep-line tie order** — process ends before starts at the same time when touching isn't overlap.
- **Check-then-insert races** in a real booking service — make them one atomic operation.

</Pitfalls>

<KeyTakeaways>

- Two intervals overlap iff each starts before the other ends.
- Sort first: by start for merging, by end for maximum selection.
- Max simultaneous overlap = rooms needed: heap of ends or ±1 sweep.
- Online bookings: a sorted map, checking only the two neighbours.

</KeyTakeaways>
