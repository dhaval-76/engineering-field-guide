## Why it matters

Looking for a value in a million sorted items by scanning takes up to a million comparisons. Binary search takes **20** — each comparison throws away half of what's left, so the work grows with log₂ n, not n. A billion items need only 30.

But the real power isn't "find a number in a sorted array". Binary search finds the **boundary of any yes/no question whose answer flips exactly once** — the first version with a bug (`git bisect`), the smallest machine size that meets a deadline, the first timestamp after a given <Term id="offset">offset</Term> in a Kafka index. Recognising that shape is the skill interviewers test.

<Callout type="analogy">
Guessing a number between 1 and 1,000 with "higher/lower" hints. Always guess the middle: at most 10 guesses, because each guess throws away half of what's left. Binary search on the answer is the same game with a different question — "is a ship of capacity 15 enough?" instead of "is the number above 500?".
</Callout>

## Recognise it

<Callout type="spot">

**Wording clues**

- The input is **sorted** (or sorted then rotated): a position, first/last occurrence, insertion point.
- "Find the **minimum** X such that…" or "the **maximum** X such that…", where feasibility is **monotone** in X (if X works, every bigger X works).
- "Minimise the maximum" or "maximise the minimum" (split an array, ship in D days, eat in H hours).
- A local property tells you which side must contain the answer (peak finding).

**Constraint clues**

- Values or answers up to 10⁹–10¹⁸ → you can't try them all, but log₂(10¹⁸) ≈ 60 checks is nothing.
- n up to 10⁵ with a feasibility check that costs O(n) → O(n log range) total.
- "Must run in O(log n)" → binary search, almost always.

**Looks like it, but isn't**

- Feasibility that is **not monotone** (works for 5, fails for 6, works for 7) → binary search gives wrong answers.
- An unsorted array with a single lookup → sorting costs O(n log n); a linear scan or a hash set is cheaper.

</Callout>

## The one template to remember

Think of every binary search as finding the **first index where a predicate becomes true** — `nums[i] >= target`, "capacity C is enough", "version v has the bug". The predicate looks like `false false false true true`, and we want the first `true`.

<Walkthrough id="first-true" />

<CodeTabs id="dsa-binary-search-template" title="First true / lower bound — the boundary template" />

- **Invariant:** the answer is always in `[lo, hi]` (with `hi = n` meaning "no element is true").
- `predicate(mid)` true → the answer is `mid` or to its left → `hi = mid`.
- false → the answer is strictly right → `lo = mid + 1`.
- The range shrinks every iteration (because `mid < hi`), so the loop ends with `lo == hi`: the first true.
- **Last occurrence** of x = (first index with `nums[i] > x`) − 1. **Count** of x = upper bound − lower bound.

**Why `lo + (hi − lo) / 2`?** `(lo + hi) / 2` can overflow when both are near the integer maximum — a real bug that sat in the JDK's own `Arrays.binarySearch` for years.

## Worked problems

### Search in a rotated sorted array

**Problem.** A sorted array was rotated at an unknown point, e.g. `[4,5,6,7,0,1,2]`. Find a target in O(log n).

<Clues>"**sorted**, then rotated" + "in **O(log n)**" → binary search; one half around `mid` is always sorted.</Clues>

**Insight.** Cut at any `mid` and **one half is still sorted** — compare `nums[lo]` with `nums[mid]` to see which. If the target lies inside the sorted half's range, search there; otherwise it must be in the other half.

| lo..hi | mid (value) | sorted half | target 0 is… | next |
|---|---|---|---|---|
| 0..6 | 3 (7) | left [4..7] | not in [4, 7) | lo = 4 |
| 4..6 | 5 (1) | left [0..1] | in [0, 1) | hi = 4 |
| 4..4 | 4 (0) | — | found | 4 |

<CodeTabs id="dsa-rotated-search" title="Search in rotated sorted array — O(log n)" />

**With duplicates** (`[1,1,1,0,1]`) you can't tell which half is sorted when `nums[lo] == nums[mid] == nums[hi]`; shrink both ends by one and continue — the worst case becomes O(n).

### Find the minimum in a rotated sorted array

<Clues>**rotated sorted** + "minimum" → binary search for the first index where `nums[i] ≤ nums[last]`.</Clues>

**Insight.** Compare `nums[mid]` with `nums[hi]`. If `nums[mid] > nums[hi]`, the drop (and so the minimum) is right of `mid`; otherwise the minimum is at `mid` or to its left. That's the first-true template with the predicate `nums[i] ≤ nums[last]`.

### Find a peak element

**Problem.** Return any index whose value is larger than its neighbours (outside the array counts as −∞). `[1,2,1,3,5,6,4]` → 5 (or 1).

<Clues>"return **any** peak" + O(log n) → binary search moving toward the larger neighbour, which must lead to a peak.</Clues>

**Insight.** The array is **not sorted**, yet binary search works: if `nums[mid] < nums[mid + 1]` you are walking uphill, and following the slope to the right must reach a peak (either the values turn down, or the array ends — and the end counts as a peak). So discard the left half. Binary search needs a rule that tells you which half certainly contains *an* answer, not full sortedness.

### Binary search on the answer: shipping capacity

**Problem.** Packages must ship in order within D days; find the smallest ship capacity. weights `[1..10]`, D = 5 → 15.

<Clues>"**smallest** capacity such that…" + bigger capacities always work (monotone) → binary search on the answer with an O(n) check.</Clues>

**Insight.** We are not searching the array — we search the **capacity**. "Can we ship within D days at capacity C?" is monotone: if C works, C + 1 works. The smallest sensible C is the heaviest package (it must fit); the largest is the sum (everything in one day). Each guess is checked greedily in O(n) — fill a day until the next package doesn't fit.

<CodeTabs id="dsa-ship-capacity" title="Minimum capacity — binary search over the answer" />

**Complexity.** O(n · log(sum)). The same shape solves *Koko eating bananas* (minimum speed), *split array largest sum* (minimum of the maximum part), *minimum days to make bouquets*, and integer square root.

### Median of two sorted arrays

**Problem.** The median of two sorted arrays in O(log(min(m, n))). `[1,3]` and `[2]` → 2.

<Clues>**two sorted** arrays + "O(log(min(m, n)))" → binary search on the split point of the shorter array.</Clues>

**Insight.** The median splits the combined data into a left half and a right half where every left value ≤ every right value. Choose how many elements `i` come from the shorter array; then `j = half − i` come from the other. The split is valid when `a[i−1] ≤ b[j]` and `b[j−1] ≤ a[i]`. If `a[i−1] > b[j]`, we took too many from `a` (move left); otherwise too few (move right). The median is then the largest left value (odd total) or the average of the largest left and smallest right (even).

<CodeTabs id="dsa-median-two-arrays" title="Median of two sorted arrays — binary search on the split" />

This is one of the hardest common interview problems; the key is to say the invariant ("left halves ≤ right halves") before coding, and to handle empty sides with ±∞.

## Binary search in real systems

- **Database indexes**: a B-tree lookup is a binary search inside each page, repeated down a few levels ([Indexing](../../databases/indexing/)).
- **<Term id="consistent-hashing">Consistent hashing</Term>**: finding a key's node is "the first ring position ≥ hash(key)" — a lower bound on a sorted ring (`TreeMap.ceilingKey` in Java) ([Consistent hashing](../../distributed-systems/consistent-hashing/)).
- **Kafka and LSM storage**: sparse offset/time indexes and SSTable block indexes are searched with binary search, then scanned briefly.
- **`git bisect`**: finds the first bad commit in log₂(commits) test runs — first-true over history.
- **Capacity planning**: the smallest instance count that meets a latency target, checked by load tests.

## Talking through it in an interview

- Name the predicate and show it is monotone before writing code ("if capacity C works, C + 1 works").
- State the invariant (`answer in [lo, hi]`) and how each branch keeps it.
- Check termination: does every branch shrink the range? `lo = mid` with a rounded-down `mid` does not.
- Test the template on a 1- and 2-element array, a target smaller than everything, and one larger than everything.

<Pitfalls>

- **Infinite loops** from `lo = mid` with `mid` rounded down — use the first-true template (`lo = mid + 1`), or round `mid` up when moving `lo`.
- **Mixing conventions** (`hi = n` vs `n − 1`, `<` vs `<=`) — pick one template and keep its invariant.
- **Overflow** in `(lo + hi) / 2` with large values.
- **Non-monotone predicates** — binary search silently returns a wrong answer.
- **Wrong bounds for answer search** — the upper bound must be feasible, or the "first true" doesn't exist.
- **Duplicates in rotated arrays** — the O(log n) guarantee breaks; handle the equal case.

</Pitfalls>

<KeyTakeaways>

- Binary search finds the boundary of a monotone predicate in O(log n).
- One invariant-based template handles first/last occurrence, insertion points and answer search.
- You need a rule that tells you which half contains an answer — sortedness is one such rule, slopes and feasibility are others.
- Search the answer space when "is X enough?" is monotone.

</KeyTakeaways>
