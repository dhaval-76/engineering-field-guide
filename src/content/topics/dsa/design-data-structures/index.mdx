## How to approach them

<Steps>

1. List every operation with its required time bound.
2. For each operation, name the structure that gives that bound alone (hash map for lookup by key, array for random index, heap for min, linked list for O(1) reordering, sorted list for range/floor queries).
3. Combine them and decide what each stores (often the map stores **positions or nodes** in the other structure).
4. Walk through each operation, updating **all** structures consistently — especially deletes.
5. State the complexity of each operation and the space.

</Steps>

<Callout type="analogy">
A library: the catalogue (hash map) tells you exactly where a book is; the shelves (array) let you grab any book at random; when a book is removed, the last book on the shelf moves into its gap and the catalogue is updated — so neither the catalogue nor the shelf ever has holes.
</Callout>

## Time-based key-value store

`set(key, value, timestamp)` with increasing timestamps; `get(key, t)` returns the value with the largest timestamp ≤ t. Per key, keep an append-only list of (timestamp, value) — already sorted — and binary-search it.

## Trie (prefix tree)

Each node has children by character and an end-of-word flag. Insert, search and prefix checks take O(L) for a word of length L. Autocomplete builds on this with top suggestions cached per node ([Autocomplete](../../low-level-design/autocomplete/)).

## Hit counter (sliding time window)

Count hits in the last 300 seconds. A queue of timestamps (or of `(second, count)` buckets) — evict old entries on each call. With a fixed window, a circular array of 300 buckets gives O(1) per operation and bounded memory.

| Requirement | Structures | Example |
|---|---|---|
| O(1) lookup + O(1) random element | map + array (swap-delete) | randomized set |
| O(1) lookup + O(1) recency order | map + doubly linked list | [LRU cache](../../low-level-design/lru-cache/) |
| O(1) lookup + frequency order | map + map of frequency → linked list | LFU cache |
| floor/ceiling by time or key | map + sorted list / TreeMap | time map, snapshot array |
| prefix queries | trie | autocomplete, word dictionary |
| min/max with O(1) push/pop | stack of (value, min) | [min stack](../stacks-and-monotonic-stacks/) |

<Pitfalls>

- **Forgetting to update the index map** when swapping elements on delete.
- **Deleting from the middle of an array** (O(n)) instead of swap-with-last.
- **Linear scans** in `get` hidden behind a map (e.g. scanning a key's whole history).
- **Unbounded growth** — old timestamps, expired hits and empty trie branches.
- **Concurrency** — real caches/registries need locks or concurrent structures.

</Pitfalls>

<KeyTakeaways>

- Derive the structure from per-operation bounds; combine and keep in sync.
- Maps store positions/nodes in the other structure; swap-delete keeps arrays dense.
- Sorted histories + binary search answer "as of time t"; tries answer prefixes in O(L).

</KeyTakeaways>
