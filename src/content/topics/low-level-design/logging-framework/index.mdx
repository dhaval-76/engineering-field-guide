## Why it matters

Every service depends on its logging library, and "design a logger" is a popular machine-coding question because it exercises several patterns at once — Strategy, Singleton/registry, Composite-like hierarchy, Decorator — plus real concurrency concerns. Knowing how it's built also explains everyday behaviour: why a log line appears twice, why DEBUG doesn't show, why logging slows a hot path.

<Callout type="analogy">
A company's mail room. Every department (logger) has a filing rule (level); if a department hasn't set one, it follows its parent division's rule. Letters that pass the rule are copied to the department's own trays (appenders) and, unless told otherwise, to every parent division's trays too. A clerk (async appender) can take the letters and file them later so staff don't wait at the cabinet.
</Callout>

## Clarify

- Levels and per-logger configuration? (Yes, by package name.)
- Destinations: console, file with rotation, remote collector? (Pluggable; console and async in code.)
- Formats: human-readable pattern and JSON? (Both.)
- Thread safety and performance? (Must not corrupt lines or block requests.)
- Request context (request id, user id) on every line? (Yes — MDC.)

## Performance

- **Check the level first** and build messages lazily (suppliers, or `{}` placeholders as in SLF4J) — disabled DEBUG calls in hot loops should cost almost nothing.
- **Async appender**: request threads only enqueue. The queue must be **bounded**; when full, choose a policy — block (safe, can slow requests), drop low levels (keeps latency), or drop and count. Never drop errors silently. Flush on shutdown.
- **Batch writes** and buffered I/O in the file appender; rotate by size or time, compress and delete old files.

## Production concerns

- **Structured (JSON) logs** with stable field names for log pipelines ([Observability](../../architecture/observability/)).
- **Context propagation**: MDC values live in thread-locals (Java), `AsyncLocalStorage` (Node) or `contextvars` (Python); copy them when work moves to another thread or task.
- **Configuration reload** at runtime: change a logger's level without restarting to debug production.
- **Security**: never log secrets or full personal data; mask by field name in the formatter.
- **Failure isolation**: an appender failing (disk full, collector down) must never crash the application — catch, count, and fall back.

<Pitfalls>

- **String concatenation before the level check** — wasted CPU on disabled logs.
- **Unbounded async queues** — an outage in the log sink becomes an out-of-memory crash.
- **Duplicate lines** from additivity when the same appender is attached at two levels.
- **Synchronous network appenders** on request threads.
- **Losing MDC context** across thread pools and async callbacks.

</Pitfalls>

<KeyTakeaways>

- Levels, a named logger hierarchy with inheritance, and additivity are the core model.
- Appenders and formatters are strategies combined freely; async appenders decorate them.
- Check levels first and build messages lazily; bound async queues with a clear drop policy.
- Structured logs with request context are what make logs useful in production.

</KeyTakeaways>
