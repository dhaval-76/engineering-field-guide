## Why it matters

LFU is the natural follow-up to [LRU](../lru-cache/): same interface, harder bookkeeping. Doing it in O(1) requires combining hash maps and ordered sets precisely, and the `minFreq` update is a classic place for bugs. It also opens a good discussion about which eviction policy fits which workload.

<Callout type="analogy">
A library with limited shelf space that removes the book borrowed the fewest times. If two books are tied, it removes the one that has sat untouched the longest. To do that instantly, the librarian keeps one shelf per borrow count, books on each shelf in the order they arrived.
</Callout>

## Clarify

- Capacity in entries (not bytes)? (Entries.)
- Does `put` on an existing key count as a use? (Yes — the common convention, e.g. LeetCode 460.)
- Tie-break? (Least recently used among the least frequent.)
- Thread safety? (Single-threaded first; discuss later.)

## Data structures

| Structure | Holds | Why |
|---|---|---|
| `entries: key → (value, freq)` | Every cached key | O(1) lookup |
| `buckets: freq → ordered set of keys` | Keys grouped by count, oldest first | O(1) move between counts; LRU order within a count |
| `minFreq` | Lowest non-empty count | O(1) to find the eviction bucket |

`LinkedHashSet` (Java), `Set` (JavaScript, insertion-ordered) and `OrderedDict` (Python) all give O(1) add, remove and "oldest element".

Why `minFreq` is easy to maintain: it only changes in two places. When a key leaves bucket `minFreq` and the bucket empties, the key is now in `minFreq + 1`, so that's the new minimum. When a new key is inserted, its count is 1, the lowest possible.

## LFU vs LRU in practice

| Aspect | LRU | LFU |
|---|---|---|
| Keeps | recently used keys | frequently used keys |
| Good for | recency-driven access (sessions, feeds) | stable popularity (assets, reference data) |
| Weakness | one big scan flushes the cache | **old popularity never fades**; new keys get evicted before they can build counts |
| Overhead | one list | buckets + counts |

Production caches combine the two: **W-TinyLFU** (Caffeine, Java's default high-performance cache) keeps approximate frequencies in a compact sketch that periodically halves (aging), and admits a new key only if it's more popular than the eviction candidate ([Caching strategies](../../distributed-systems/caching-strategies/)). <Term id="redis">Redis</Term> offers `allkeys-lfu` with a logarithmic counter that decays over time.

## Concurrency and extensions

- **Thread safety**: one lock around get/put is simplest and correct (every get mutates structure). For high throughput, shard by key hash into N independent caches, or buffer accesses and apply them in batches as Caffeine does.
- **Aging**: periodically halve all counts, or decay counts by time since last access.
- **<Term id="ttl">TTL</Term>**: store an expiry per entry; check on get and evict expired entries lazily.
- **Size-based capacity**: track total weight; evict until under the limit.

<Pitfalls>

- **Forgetting that `put` to an existing key is an access** — counts drift from the spec.
- **Not resetting `minFreq = 1`** after inserting a new key.
- **Scanning all keys to find the minimum** — O(n) eviction.
- **Ignoring ties** — the spec needs <Term id="lru">LRU</Term> among equal counts.
- **Capacity 0** — guard it explicitly.

</Pitfalls>

<KeyTakeaways>

- Map of entries + map of frequency buckets (insertion-ordered) + `minFreq` gives O(1) LFU.
- `minFreq` changes only when its bucket empties on access (→ +1) or on insert (→ 1).
- Pure LFU needs aging; real caches use approximate frequencies (W-TinyLFU, Redis LFU).

</KeyTakeaways>
