## Why it matters

Every call to an LLM is billed by the token, and an API is stateless, so a chat or an agent resends its whole history on every turn. A 20-step agent with a large system prompt pays for those same instructions 20 times. Cost and latency are usually the first production problems after launch, and "how would you reduce inference cost?" is a standard interview follow-up.

Prompt caching is the rare optimisation with no quality trade-off: the model output is the same, you pay less, and the response starts sooner.

<Callout type="analogy">
A long-form exam where every candidate must first read the same 50-page rule book. Without caching, each one reads it from scratch. With caching, the exam centre keeps a summary of "someone who has read exactly this rule book" ready to go. Change one word on page 1, and the summary is useless: it was built for the old text.
</Callout>

## How prompt caching works

To answer, a model first processes the prompt from start to end. The intermediate result depends only on the text so far, so the provider can keep it and resume from it. That is why **only a prefix can be reused**: a change at position N invalidates everything after N.

### Things that silently break the cache

| In the prefix | Fix |
|---|---|
| Current date or time, request id, user name | Move it after the cached part |
| Tools built in a different order each time | Sort them |
| JSON with unstable key order | Serialise deterministically |
| Tools that differ per user | Give everyone one tool set; check permissions in code |
| Editing or trimming old chat messages | Keep history append-only, or accept a miss when you compact |
| Switching models | Caches are per model |

You get no error when this happens, just a larger bill. So **log the cached-token count from every response** and alert on the hit rate.

### What the main providers do

These change often. The table was checked against each provider's documentation on 9 November 2026.

## Doing the arithmetic

Take a support assistant with a 10,000-token prefix, 300 new input tokens, 400 output tokens and 100,000 requests. The prices are illustrative: $3 per million input tokens and $15 per million output, writes at 1.25× and reads at 0.1×.

Three things to notice:

- **One read repays a 5-minute write** (1.25 + 0.1 is less than 2). A 1-hour write at 2× needs two reads. Use the longer lifetime only if requests are too far apart for the short one.
- **Traffic pattern decides the hit rate.** A cache entry that expires between requests never gets read. Low-traffic features may get no benefit at all.
- **Output is now half the bill.** It was $600 of $3,690 before, and it is $600 of $1,162.50 after. Once input is cached, cutting output length matters most.

## Three different caches

People use "cache" for all of these, and an interviewer will check that you can tell them apart.

| | Provider prompt cache | Exact response cache | Semantic cache |
|---|---|---|---|
| Stores | The model's processed prefix | The final answer | The final answer |
| Key | Exact prompt bytes | Hash of the whole prompt | Embedding of the question |
| Model still runs? | Yes | No | No |
| Can the answer be wrong? | No | Only if stale | **Yes**, a near match may need a different answer |
| Savings | Input tokens | Whole call | Whole call |
| Main risk | Low hit rate | Staleness | Wrong answers, and data leaking between users |

Semantic caching looks attractive and is often a mistake. "Can I cancel my order?" and "Can I cancel my subscription?" are close together in embedding space. It suits a narrow set of public, frequently asked questions with no personal data, a strict similarity threshold, and an eval that measures how often it returns the wrong thing. Scope any cache key by tenant and permissions.

## The other cost levers

Work down this list. The first group costs you nothing in quality.

| Lever | Effect | Trade-off |
|---|---|---|
| Prompt caching | Large on repeated prefixes | None, once the layout is right |
| Shorter prompts, fewer retrieved chunks | Directly fewer tokens | Check retrieval quality |
| Limit output length, ask for concise answers | Output is the expensive side | Check answers aren't cut off |
| Batch API for work that can wait | Usually half price | Results take up to hours |
| Exact response cache | Removes the call | Staleness; needs real repeats |
| Route easy requests to a smaller model | Often the largest saving | Needs evals per route, and caches are per model |
| Fewer agent steps, step limits | Cuts repeated full-context calls | May reduce completion rate |
| Self-hosted models | Pays off only at high steady volume | Large operational cost |

**Measure cost per completed task, not cost per call.** A cheaper model that needs a retry, or an extra agent loop, or a human escalation, may cost more overall.

**Budgets stop accidents.** Enforce per-user and per-tenant token limits in the [LLM gateway](../llm-system-design/), set a maximum step count on agents, and alert on spend per feature. A loop bug with no limit can burn through a month's budget overnight.

<Pitfalls>

- **Putting a timestamp or user name at the top of the system prompt.**
- **Assuming caching is working.** Check the cached-token count in responses.
- **Caching prompts that have no stable prefix.** You pay the write premium and never read it.
- **Prefixes below the minimum size.** Nothing happens, and no error says so.
- **Routing to a cheap model without an eval.** You save money and lose quality, and only find out from users.
- **Semantic cache keys that ignore tenant or permissions.**

</Pitfalls>

<KeyTakeaways>

- Prompt caching reuses an exact prefix: it never changes the answer.
- Lay out prompts from most to least stable and test that the prefix holds.
- Monitor the hit rate; a low one costs more than no cache.
- Prompt cache, response cache and semantic cache are different tools with very different risks.
- Judge savings by cost per completed task, verified with evals.

</KeyTakeaways>
